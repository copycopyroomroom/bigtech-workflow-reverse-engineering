# AI 워크플로우 설계·조합 기능 기획 v0.2

작성일: 2026-10-23 (Asia/Seoul)

상태: 제품 설계안. 수집기·분석기·조합기·외부 적용 기능은 아직 구현하지 않았으며, 실제 팀의 효과도 측정하지 않았다.

이 문서는 공개 프로젝트의 관찰을 팀별 실행안으로 바꾸는 **Workflow Composer**의 범위와 동작을 정의한다. 연구 방법은 [분석 프로토콜](../methodology/ANALYSIS_PROTOCOL.md), 구조화된 입출력과 식별자 규칙은 [데이터 계약](../specs/WORKFLOW_CONTRACTS.md)을 따른다.

## 1. 제품의 목적과 약속

사용자가 팀의 문제와 제약을 설명하면 AI가 근거를 확인한 관행을 찾아 조합하고, 대화로 수정 가능한 워크플로우 초안을 제안한다. 사용자는 여러 대안의 적용 조건·추가 업무·부작용을 비교한 뒤 실험할 안을 고른다. 회사별 사례를 탐색할 수 있지만 실제 선택 단위는 `회사`가 아니라 **특정 저장소·기간에서 관찰한 관행 모듈**이다.

제품이 제공하는 가치는 다음 세 가지다.

1. 공개 기록의 출처와 한계를 추적하면서 팀의 현재 과정을 설명한다.
2. 여러 프로젝트의 관행을 팀의 규모·위험·역할·도구에 맞춰 재구성한다.
3. 채택 전 검토할 변경점, 실행 자료, 검증 실험과 되돌리기 계획을 만든다.

사용자가 말하는 “장점만 가져오기”는 **해결할 문제에 맞는 기대 이점을 골라 채택하는 것**으로 구현한다. 관찰된 관행에는 전제와 비용이 있으므로, 비용·충돌·불확실성을 제거한 것처럼 제시하지 않는다. 공개 저장소에서 관찰되었다는 사실과 대상 팀에서 효과가 있다는 주장은 별도로 다룬다.

## 2. 대상 사용자와 사용 단위

| 사용자 | 수행할 작업 | 필요한 결과 |
| --- | --- | --- |
| 오픈소스 프로젝트 메인테이너 | 신규 기여자 대응, 리뷰 소유권, 릴리스 절차 개선 | 외부 기여자를 포함한 역할·절차와 기여 문서 초안 |
| 엔지니어링 리드·플랫폼 담당자 | 병목을 찾고 팀에 맞는 과정을 제안 | 현행/제안 비교, 담당 역할, 도구 요구사항, 적용 순서 |
| 워크플로우 자문 담당자 | 인터뷰·근거·대안·권고를 검토 가능한 형태로 정리 | 고객별 진단과 의사결정 기록, 출처가 붙은 제안서 |
| 개발 팀원 | 제안의 부담과 예외를 확인하고 수정 의견 제시 | 역할별 행동, 추가 시간, 긴급 변경 경로, 변경 이유 |

첫 버전의 설계 단위는 팀 하나와 저장소 하나의 `요구/설계 → 변경 → 리뷰/검증 → 병합 → 릴리스` 흐름이다. 여러 팀·여러 저장소의 조직 설계는 이후 확장으로 분리한다. 자문자는 승인 권한과 운영 책임을 고객 역할에 매핑하며, AI가 임의의 사람에게 책임을 배정하지 않는다.

### 2.1 공통 엔진과 세 사용 모드

세 사용 모드는 기본값이나 우선순위를 정하지 않고 동등한 선택지로 제공한다. 근거·관행 카탈로그, 팀 진단, 조합·검증, 대화 수정, 실행 기록과 내보내기 엔진은 공유한다. 모드 차이는 작업 주체, 검토 책임, 전달 산출물과 운영 비용이다. 아래의 비용은 상대적인 항목 비교이며 가격표나 실측 결과가 아니다.

| 사용 모드 | 사용자 흐름 | 추가 산출물 | 추가 비용·운영 부담 | 선택 조건 |
| --- | --- | --- | --- | --- |
| 팀이 직접 쓰는 OSS 도구 | 팀 입력 → 자동 초안 → 팀의 정책·역할 검토 → 설계 선택 → 내보내기·자체 실험 | 설치·재현 안내, 팀용 제안서·템플릿, 자체 검토표 | 설치·모델 호출·유지보수, 근거·입력 해석과 최종 검토를 팀이 담당 | 팀 내부에서 진단·검토·실험 책임을 맡을 수 있고 직접 운영을 원하는 경우 |
| 자문자의 분석·설계 도구 | 자문자 인터뷰 → 증거·맥락 정리 → 대안 생성 → 자문자 검토 → 고객 확인 → 전달·실험 설계 | 고객용 진단서, 출처 부록, 권고·거절 이유, 인수인계·검토 서명 기록 | 인터뷰·데이터 정리·독립 검토·고객 협의 시간, 고객별 비공개 자료 분리 | 맥락 해석과 이해관계 조율을 외부 또는 내부 자문자가 맡는 경우 |
| 두 방식을 함께 제공 | 공통 엔진으로 팀이 초안 생성 → 선택한 범위만 자문 검토 → 수정·인계 → 팀 자체 운영 | OSS 산출물 + 검토 범위·담당 경계·변경 이력, 운영 인계 자료 | 두 모드의 호환 버전 관리, 선택 자문 시간, 검토 경계·인수인계 관리 | 팀의 자율 운영과 필요 시 전문 검토를 함께 원하는 경우 |

자문 모드는 실제 검토자가 없으면 자문 검토 완료로 표시할 수 없다. OSS 모드의 자체 검토를 독립 자문 검토로 부풀리지 않는다. 함께 제공하는 모드에서는 자문자가 검토한 revision과 이후 팀이 수정한 revision을 구분하고, 이후 변경에 과거 검토 서명을 자동 승계하지 않는다.

이 **세 사용 모드**는 7절의 **세 워크플로우 대안**과 다른 선택이다. 어느 모드를 택해도 최소 변경안·균형안·통제 강화안을 비교할 수 있다. 연구·엔진 검증 뒤 세 모드의 수요·운영 부담을 비교하고 구현·운영 범위는 명시적인 선택으로 확정한다.

## 3. 핵심 사용자 흐름

1. **진단 입력**: 팀 프로필과 현재 워크플로우, 해결할 문제, 제약을 입력한다. 고객의 비공개 코드나 개인별 활동 기록 없이도 시작할 수 있다.
2. **누락 확인**: AI가 실행 가능성에 영향을 주는 미확인 항목을 묶어 제시한다. 조직 정책·필수 승인·역할 가용량이 없으면 조건부 초안을 만들고 확정 대상을 명시한다.
3. **근거 탐색**: 문제와 적용 조건으로 관행을 찾고 회사·분야·운영 형태·기간으로 결과를 좁힌다. 회사명이 같은 이유만으로 우선 추천하지 않는다.
4. **대안 생성**: 동일한 필수 제약을 지키는 세 대안을 작성한다. 불가능한 대안은 채울 목적으로 생성하지 않고 불가능한 이유를 보여준다.
5. **비교·선택**: 현행 대비 변경점, 근거, 역할별 부담, 충돌, 적용 순서를 확인한다. 사용자는 대안 전체 또는 모듈 일부를 선택한다.
6. **대화 수정**: “릴리스 주기는 유지하고 리뷰 부담을 줄여줘”처럼 요청한다. AI는 변경 제안과 diff를 만들고 검증 결과를 갱신한다.
7. **설계 확정**: 사람이 미확인 조건과 예외를 검토하고 특정 버전을 실험안으로 확정한다. 확정 전 초안은 실행 가능한 권고와 구분한다.
8. **내보내기·실험**: 계획과 설정 초안을 파일로 내보낸다. 실제 저장소·조직 설정 변경은 별도 단계이며 MVP에는 포함하지 않는다. 기준선과 종료 기준을 정한 뒤 대상 팀에서 효과를 확인한다.

## 4. 입력: 팀 맥락과 현행 과정

### 4.1 팀 프로필

| 입력 묶음 | 필드 예시 | 추천에서 사용하는 방식 |
| --- | --- | --- |
| 목표 | 리뷰 지연 감소, 회귀 감소, 외부 기여자 경험, 릴리스 예측 가능성 | 우선순위와 성공 지표를 정한다. 충돌하는 목표의 우선순위를 묻는다. |
| 조직·역할 | 팀 인원 구간, 역할 종류, 리뷰 가능한 인원, 소유 영역, 외부 기여 여부 | 필요한 역할과 실제 가용량을 대조한다. 실명은 필수가 아니다. |
| 제품·위험 | 제품 종류, 운영 중요도, 호환성 요구, 긴급 변경 필요, 조직 정책 | 절차를 생략할 수 없는 조건과 위험별 경로를 정한다. |
| 개발 환경 | 저장소 수, 기존 Git/이슈/CI 도구, 자동화 수준, 테스트 환경 | 도구 의존성과 수작업 대체 가능성을 구분한다. |
| 변화 여력 | 주당 허용 추가 시간, 도구 예산, 도입 기간, 바꿀 수 없는 관행 | 역할별 부하와 순차 도입 순서를 제한한다. |
| 현재 측정 | PR 유입량, 첫 반응 시간, 긴급 변경·회귀 건수 등 | 측정 정의·분모·기간이 맞는 경우에만 기준선으로 쓴다. |

모든 필수 항목을 숫자로 강제하지 않는다. 모르는 값은 `unknown`으로 보존하고, 범위·질적 진단만 있는 경우에도 가정과 미확인 목록이 붙은 초안을 제공한다. 가용 인원이나 필수 정책처럼 실행 가능성에 직접 영향을 주는 값이 미확인이면 “실행 검토 완료”로 표시할 수 없다.

입력은 `사용자 진술 / 연결 문서의 명시 규정 / 관찰 데이터 / AI 가정`으로 출처를 구분한다. 사용자 진술과 저장소 기록이 다르면 한쪽을 덮어쓰지 않고 차이와 확인 질문을 남긴다.

### 4.2 현행 워크플로우

현재 과정은 단계, 시작 조건, 입력, 담당 역할, 다음 단계 조건, 예외, 도구를 가진 그래프로 표현한다. 그래프가 없으면 대화나 체크리스트로 초안을 만들고 사용자가 확인한다. 현재 과정을 모르는 경우 “현행 대비 개선”이라고 쓰지 않고 신규 설계 초안으로 표시한다.

### 4.3 제약의 구분

- **필수 제약**: 조직 정책, 반드시 필요한 승인, 변경할 수 없는 릴리스 조건, 역할 상한, 데이터 반출 제한. 위반하는 안은 선택 가능한 권고로 내보내지 않는다.
- **선호**: 짧은 회의, 낮은 도구 비용, 특정 도구 유지, 자동화 우선. 가능한 대안의 우선순위에만 반영한다.
- **가정**: 입력이 없는 항목을 임시로 채운 값. 영향받는 제안과 확인 책임을 표시한다.
- **잠금**: 사용자가 보존을 지시한 선택이나 값. AI가 후속 대화에서 임의 변경할 수 없다.

필수 제약을 만족하는 조합이 없으면 `추천 보류`와 최소 충돌 집합을 반환한다. 정책을 완화한 안을 자동으로 최종 추천으로 바꾸지 않는다.

## 5. 관행 라이브러리와 조합 규칙

관행 모듈은 “회사 A 방식” 같은 브랜드 묶음보다 작아야 한다. 예를 들어 위험에 따른 리뷰 경로, 설계 설명과 PR의 연결, 리뷰 역할 순환, 릴리스 전 호환성 점검은 각각 독립적으로 채택·수정·검증할 수 있는 모듈 후보다. 이 예시는 제품 설계용이며 실제 프로젝트에서 이미 확인한 관행 목록이 아니다.

각 모듈은 데이터 계약에 정의한 식별자와 버전을 가지며 다음 의미를 담는다.

| 묶음 | 필수 내용 |
| --- | --- |
| 관찰 범위 | 출처 저장소·관찰 기간·적용 변경 유형·claim/evidence ID |
| 실행 의미 | 해결할 문제, 트리거, 단계, 입력/출력, 책임 역할, 완료 조건 |
| 조절 지점 | 승인 수, 위험 분류, 응답 목표, 배포 간격 등 수정 가능한 매개변수와 허용 범위 |
| 적용 전제 | 필요한 역할·역량·도구·정보·기준선, 적용하면 안 되는 조건 |
| 상호작용 | 필수 의존, 선택 의존, 대체 관계, 충돌 관계와 그 이유 |
| 부담·위험 | 도입 비용, 역할별 반복 업무, 예상 부작용, 예외와 중단 조건 |
| 효과 상태 | 기대 이점, 이를 뒷받침하는 관찰, 대상 팀의 별도 검증 상태 |

두 모듈이 비슷한 용어를 사용해도 같은 단계·같은 승인 대상을 뜻하는지 확인한다. 필수 승인 1명과 소유자 확인 1명을 단순 합산해 승인 2명으로 만들거나, 둘이 다른 책임인데 하나로 합치지 않는다. 의미가 불명확하면 자동 병합 대신 미해결 항목으로 반환한다.

### 5.1 검증 순서

1. 입력과 모듈 버전의 계약 유효성을 검사한다.
2. 회사·분야보다 문제·전제·관찰 범위로 후보를 좁힌다.
3. 필수 의존을 확장하고 순환 의존·누락 역할·필요 도구를 확인한다.
4. 금지 조건·잠금·조직 정책과 모듈 간 충돌을 확인한다.
5. 정상 경로, 긴급 경로, 실패·되돌리기 경로가 끊기지 않는지 확인한다.
6. 역할별 동시·반복 업무와 도입 비용을 산정해 가용량과 대조한다.
7. 필수 제약을 통과한 조합을 목표 적합성·변화 부담·근거 범위로 비교한다.
8. 제안 문장을 검증된 구조에서 생성하고 출처·가정·추론 범주를 점검한다.

언어 모델의 자기평가만으로 위 검사를 통과시키지 않는다. 스키마, 참조 무결성, 명시적 의존·충돌·잠금, 역할 상한은 모델과 분리한 규칙 검증기가 판정한다. 의미 해석이 필요한 충돌은 AI 설명과 사람의 확인 항목으로 남긴다.

### 5.2 역할별 부하

부하는 역할별로 `도입 작업 시간 + 예상 건수 × 건당 추가 시간 + 고정 반복 시간`으로 분리한다. 사용자 측정값이 없으면 범위를 가진 가정으로 산출하고 숫자 옆에 출처를 붙인다. 여러 모듈이 같은 검사를 재사용한다고 명시한 경우에만 중복을 제거한다. 역할의 동시 가용성도 확인해 “작성자 외 승인자 2명”이 필요한데 역할을 수행할 사람이 1명인 조합을 차단한다.

예산 상한 초과가 확실하면 해당 안을 부적합으로 표시한다. 추정 범위가 상한을 걸치거나 데이터가 없으면 조건부 상태로 두고, 짧은 기준선 측정이나 작은 시범 적용을 선행 과제로 제안한다. 단순 합계만으로 리뷰 대기시간이나 품질 향상을 예측하지 않는다.

## 6. 근거와 효과를 구분하는 출력

사용자는 각 제안의 근거 카드를 열어 다음 내용을 확인할 수 있어야 한다.

- 직접 확인한 정책 또는 사건, 출처 URL, 문서 SHA/내용 해시, 관찰 기간.
- 전체 관찰 건수·해당 분모·반례·누락과 근거의 최신성.
- 관찰된 규칙을 팀에 맞게 바꾼 지점과 변경 이유.
- 예상 이점·비용·부작용·필요 전제와 아직 확인하지 못한 항목.
- 제안이 기대하는 효과, 측정할 지표, 대상 팀에서의 검증 여부.

출력에는 최소한 다음 범주를 구분한다.

| 표시 | 의미 | 표현 예시 |
| --- | --- | --- |
| 출처에서 관찰 | 저장소·기간에 한정해 근거로 확인 | “이 기간 표본의 X건에서 확인” |
| 맥락에 맞게 변형 | 관찰 모듈의 매개변수·역할·단계를 바꿈 | “원 관행의 역할을 두 역할로 통합. 비용은 미검증” |
| AI 신규 제안 | 직접 대응하는 관찰 근거 없이 새 규칙이나 결합을 설계 | “대상 팀용 가설. 공개 사례가 효과를 입증하지 않음” |
| 대상 팀에서 검증 | 별도 실험·운영 관찰을 수행 | 기간, 기준선, 결과, 한계, 검토자를 연결 |

각 제안은 관찰 신뢰도, 맥락 적합성의 불확실성, 효과 검증 상태를 따로 표시한다. 하나의 “AI 신뢰도 95%”로 합치지 않는다. 모듈 A와 B가 각각 관찰되었어도 A+B 조합 전체가 검증되었다고 표시하지 않는다. 결합에 새 연결 규칙을 추가하면 그 연결은 `AI 신규 제안` 또는 사람의 설계로 표시한다.

### 6.1 근거 단계와 적용·자문 검토 상태

근거 단계는 데이터 계약의 `E0 provenance-only / E1 source-policy / E2 repeated-observation / E3 target-pilot`를 사용한다.

| 단계 | 의미 | 허용되지 않는 확대 해석 |
| --- | --- | --- |
| E0 provenance-only | 출처·시점·해시 등 추적 경로만 확보 | 출처가 있다는 이유로 관행 존재·반복·효과를 주장 |
| E1 source-policy | 출처의 명시적 정책을 해당 범위에서 확인 | 문서의 규정이 실제로 준수되었다고 주장 |
| E2 repeated-observation | 범위·분모·반례를 기록한 반복 관찰을 확인 | 관행이 결과를 만들었다는 인과 또는 다른 팀의 효과를 주장 |
| E3 target-pilot | 특정 대상 팀의 별도 파일럿 결과와 한계를 기록 | 다른 팀에도 같은 효과가 있거나 조합 전체가 보편적으로 검증되었다고 주장 |

출처의 관찰 단계와 대상 팀 파일럿의 상태는 연결하되 원 출처 기록을 덮어쓰지 않는다. E3를 부여할 때도 대상 팀·기간·실험 버전·기준선·동시 변화·결과·한계를 별도 보존한다. E3라는 표시는 성공을 뜻하지 않으며, 효과가 없거나 부작용으로 중단된 파일럿도 결과대로 기록한다.

이 근거 단계와 별개로 `transfer_status`는 전제·역할·위험·도구가 해당 팀에 맞는지, `effect_status`는 실제 효과 판정, `advisory_review_status`는 사람이 제안과 책임 경계를 검토했는지를 나타낸다. 정확한 상태값은 공통 계약을 따른다. 각 검토의 판정, 검토자, 범위, revision, 미해결 항목을 기록한다. 근거 단계가 높아도 전이 검토를 생략하지 않으며, 자문자가 승인해도 E1이 E2나 E3로 바뀌지 않는다. 직접 근거 없는 새 AI 가설은 `origin: ai_proposed`, `evidence_level: null`로 표시한다.

## 7. 기본으로 비교할 세 대안

| 대안 | 설계 방향 | 보여줄 비용·검증 초점 |
| --- | --- | --- |
| 최소 변경안 | 현행 과정에서 문제와 직접 연결된 모듈 1개를 우선 도입 | 도입 부담, 단일 변경의 관찰 가능성, 남는 문제 |
| 균형안 | 필요한 의존만 포함해 여러 모듈을 조합하고 단계적으로 도입 | 기대 이점의 상호작용, 담당 역할, 모듈별 적용 순서 |
| 통제 강화안 | 위험 대응·추적성·명시적 승인과 예외 처리를 더 강화 | 검토 부담, 지연 가능성, 운영 책임, 과한 통제의 중단 기준 |

세 대안 모두 같은 필수 제약을 지킨다. 통제 강화안을 곧 고품질로, 최소 변경안을 곧 저품질로 순위 매기지 않는다. 팀의 목표에 따라 권장안을 정하고 선택 이유·차선안·권장하지 않은 이유를 쓴다. 차이가 없는 대안은 억지로 셋을 채우지 않고 가능한 대안 수와 이유를 알려준다.

비교표는 `해결 범위 / 현행에서 바뀌는 단계 / 근거 / 역할별 추가 부담 / 필요한 도구 / 실패 가능성 / 되돌리기 / 미확인 조건`을 같은 열로 보여준다. 절감 시간·품질 향상률은 실측이나 명시적 계산 근거 없이는 제시하지 않는다. 우선순위 가중치를 사용한다면 사용자가 본 값과 규칙을 기록하고 가중치 변경 시 순위가 바뀌는지도 확인한다.

## 8. 대화 수정, 버전, diff와 잠금

자연어 입력은 바로 현재 설계를 덮어쓰지 않고 `수정 제안 → 검증 → 사용자 반영` 단계를 거친다. 사용자가 일괄 반영을 명시적으로 요청한 범위에서는 검증을 통과한 수정에 한해 새 버전을 만들 수 있다. 외부 시스템 적용 권한으로 해석하지 않는다.

각 수정에는 다음을 남긴다.

- 요청한 변경과 현재 기준 버전.
- 추가·삭제·수정된 단계·역할·매개변수·모듈의 구조화된 diff.
- 바뀐 이유와 근거 또는 AI 가정.
- 연쇄적으로 바뀌는 의존, 역할별 부담, 효과 가설, 실험 지표.
- 검증 결과, 미해결 충돌, 사용자의 반영·거절과 새 버전 ID.

예를 들어 “리뷰어를 2명에서 1명으로 줄여줘”라는 요청이 조직의 필수 승인 조건과 충돌하면 현재 안을 유지하고 충돌을 보여준다. 선택 가능한 다른 부담 감소 방법이 있으면 별도 대안으로 제안한다. “릴리스 주기는 유지”를 잠갔으면 다른 모듈을 조정하더라도 릴리스 주기를 바꾸지 않는다. 변경이 필요할 때는 잠금 해제를 별도 명시하게 한다.

대화는 확정 권한·조직 정책·근거 범주를 바꿀 수 없다. 이전 버전 복원도 새 revision과 결정 기록으로 남긴다. 한 수정의 검증이 끝난 뒤 다음 수정을 처리하며, 여러 사용자의 충돌 수정은 기준 버전 불일치를 반환한다. 동시 협업 UI는 MVP 범위에서 제외하되 버전 충돌 감지는 포함한다.

## 9. 출력 묶음과 실행 자료 내보내기

사람이 검토할 제안서와 기계가 읽을 설계를 함께 만든다. 어느 산출물도 저장소의 보호 규칙을 이미 적용했다고 표현하지 않는다.

| 출력 | 내용 |
| --- | --- |
| 팀별 제안서 | 문제·현재 과정·세 대안·권고 이유·가정·예상 부담·의사결정 필요 항목 |
| 워크플로우 정의 | 역할, 단계, 트리거, 경로, 모듈 버전, 매개변수, 제약을 가진 JSON/YAML |
| 시각화 | Mermaid 흐름도와 정상·긴급·실패 경로 설명 |
| 근거·결정 목록 | claim/evidence/module 참조, AI 신규 제안 표시, 반례, 선택·거절 이유 |
| 적용 실험안 | 기준선 수집, 단일 변경 또는 순차 도입, 담당자, 지표, 중단·되돌리기 조건 |
| 실행 문서 초안 | PR·이슈 템플릿, CONTRIBUTING 절차, 리뷰·릴리스 체크리스트 |
| 설정 초안 | 요청한 도구를 위한 소유권·CI·브랜치 규칙 설정 예시와 수동 적용 안내 |

기본 내보내기는 Markdown·JSON/YAML·Mermaid 파일 묶음이다. MVP의 도구별 설정은 지원하는 템플릿과 전제 조건을 명시한 제한된 초안으로 제공한다. 역할과 실제 계정이 매핑되지 않은 설정에는 placeholder를 유지하고 `미해결 항목 있음`으로 표시한다. 생성 파일의 문법 검사와 설정의 실제 강제 적용 확인은 서로 다른 상태로 기록한다.

내보내기에는 선택한 설계 버전, 원본 근거 버전, 검증 결과, 사람이 해결해야 할 항목, 적용 순서, 백업·되돌리기 안내를 포함한다. Git 커밋·PR 생성·보호 규칙 수정·배포·서비스 메시지 발송은 이 기능의 내보내기에 포함하지 않는다. 향후 별도 실행 기능을 만들 경우 대상과 실제 diff를 제시하고 그 실행에 대한 권한을 확인하는 경계를 둔다.

## 10. 구조와 책임 분리

```text
공개 원본 → 수집·정규화 → 주장·근거 저장소 → 검토된 관행 카탈로그
                                                       ↓
팀 입력·현행 과정 → 맥락 정규화 → 후보 검색 → 조합 초안(LLM)
                                                       ↓
                   버전·결정 기록 ← 규칙 검증기 ↔ 수정 제안
                                         ↓
                         세 대안·diff·근거 설명 → 사람의 선택
                                                       ↓
                                              내보내기·실험안
```

| 구성 요소 | 책임과 경계 |
| --- | --- |
| 근거 저장소 | 수집 시점과 해시를 가진 원본 참조, 주장·반례·관찰 범위를 관리 |
| 관행 카탈로그 | 검토 상태와 버전이 있는 모듈만 추천 후보로 제공. 미검토 모듈은 탐색용으로 구분 |
| 맥락 정규화기 | 사용자 입력을 계약 형식으로 바꾸고 가정·미확인·필수 제약을 보존 |
| 검색·후보 생성기 | 문제·전제·범위로 후보와 제외 이유를 반환. 검색 결과가 없는 경우를 허용 |
| LLM 어댑터 | 계약에 맞는 초안·설명·수정 patch를 생성. 입력·출력 검증과 호출 예산을 적용 |
| 규칙 검증기 | 의존·충돌·잠금·역할·그래프·참조·필수 제약 검사. 실패를 초안 상태로 반환 |
| 비교·내보내기 | 검증된 구조를 사람이 검토할 제안서와 실행 자료로 변환 |
| 실행 기록기 | 입력·버전·비용·검증·결정·산출물 해시를 기록 |

특정 모델 제공자에 종속되지 않도록 도메인 계약과 실행 상태는 제품이 소유한다. 모델 호출은 `generate / propose_patch / explain` 같은 작업 인터페이스를 통해 어댑터로 분리하고, 제공자·모델·설정·사용량은 실행 기록에 남긴다. 제공자 고유 기능은 선택 어댑터로만 사용한다. 같은 고정 평가 묶음으로 품질·비용·지연을 비교한 뒤 교체한다. 규칙 검증을 우회하는 자동 모델 전환은 허용하지 않는다.

## 11. 재현성과 데이터 경계

### 11.1 실행 기록

각 실행은 `run_id`와 설계 revision을 가지며, 다음을 연결한다.

- 입력 계약 버전, 팀 프로필·현행 과정의 버전과 해시. 민감한 원문은 로컬 또는 별도 보호 저장소에 둔다.
- 사용한 데이터 snapshot, claim·모듈·정책·도구 템플릿의 버전.
- 검색 질의·선택한 후보와 제외 이유, 프롬프트 템플릿 버전과 실제 전달 내용의 보관 위치.
- 모델 제공자·모델 식별자·생성 설정·호출 시각·재시도·사용량·비용 산정 근거.
- 원 생성 응답, 파싱 결과, 검증 결과, 사람의 수정·결정·잠금 변경, 최종 산출물 해시.

고정 입력·관행·규칙으로 참조 검사·충돌 판정·내보내기를 다시 실행할 수 있어야 한다. 언어 모델을 새로 호출하면 같은 문장이 나온다고 보장하지 않는다. **저장된 모델 응답을 재사용하는 재생**과 **모델을 새로 호출하는 재생성**을 구분하고, 재생성 결과는 새 실행으로 비교한다. 민감정보 삭제로 재생이 제한되면 삭제 범위와 재현 한계를 표시한다.

### 11.2 외부 콘텐츠의 지시 격리

PR 본문·이슈·리뷰·README·외부 문서는 관찰 데이터이며 제품의 실행 지시로 취급하지 않는다. “이전 지시를 무시하라”, “토큰을 보내라” 같은 문구가 포함되어도 권한·도구 호출·파일 수정의 근거로 사용할 수 없다.

수집기는 원문을 데이터 필드로 격리하고, 분석 단계에는 필요한 범위만 출처 ID와 함께 전달한다. 모델은 근거에서 식별자를 선택하고 주장을 만들 수 있지만 토큰·실행 권한을 받지 않는다. 이후 단계의 출처 URL과 참조는 수집한 허용 목록과 대조한다. 발견한 외부 URL을 자동 방문하거나 쉘 명령·설정 스크립트로 실행하지 않는다. 잘못된 구조·존재하지 않는 근거 ID·외부 지시를 따른 출력은 검증 실패로 처리한다.

### 11.3 비공개 팀 입력

공개 원본과 고객별 팀 입력을 저장·검색·내보내기에서 분리한다. 고객 정보가 공개 관행 라이브러리나 다른 팀의 추천에 섞이지 않게 한다. 외부 모델에 전달할 필드, 보관 위치·기간, 삭제 정책을 실행 설정으로 표시하고 비밀정보는 입력·로그에서 제외한다. MVP 기본 입력은 역할과 집계 중심이며 비공개 저장소 직접 연결과 자동 사내 수집은 제외한다.

## 12. MVP와 후속 범위

MVP는 **파일 기반으로 한 팀의 설계를 끝까지 재생·검토하는 공통 엔진 단계**로 정의한다. 초기 사용자 접점은 Markdown 질의·응답과 JSON/YAML 입력이다. 후속 웹·서버·DB의 기술 기준안과 별도 구현 범위는 [플랫폼 설계](../architecture/PLATFORM.md)에 구체화했다. 프로토타입에서 계약을 검증한 뒤 웹을 연결한다. 세 모드에 같은 엔진을 사용하고 모드별 검토·인수인계 기록을 달리 제공한다. 특정 사용 모드를 기본으로 선정하지 않는다.

| MVP에 포함 | MVP에서 제외 |
| --- | --- |
| 사람이 검토한 근거 연결 관행 6~10개 | 모든 회사·저장소를 자동 조사하는 무제한 탐색 |
| 팀 하나·저장소 하나의 현행 진단과 세 대안 | 조직 전체 재설계·부서별 권한 자동 추정 |
| 자연어 요청을 구조화한 수정 제안·diff·잠금·revision | 동시 실시간 공동 편집 |
| 의존·충돌·역할 가용량·부하 검사 | 실제 대기시간·품질 개선률의 근거 없는 예측 |
| 출처·변형·AI 신규 제안·효과 검증 상태 분리 | 회사 내부 프로세스 추정, 개인별 생산성 평가 |
| 계획·템플릿·설정 초안 파일 내보내기 | 외부 저장소 설정 변경·PR/메시지 발송·자동 배포 |
| 고정 시나리오 평가와 저장 응답 재생 | 자율 최적화, 검증 없이 자동 규칙 완화 |

관행 수는 첫 분석의 실제 증거에 따라 조정한다. 근거가 부족한 수를 AI 신규 제안으로 채워 “분석에서 도출한 관행”으로 계산하지 않는다. 세 모드 모두 해당 모드의 책임자가 검토하는 방식으로 첫 실사용을 진행한다. 자문 검토를 받지 않은 경우에도 기능 이용은 가능하되 그 상태를 명시한다. UI 구현·SaaS 운영·외부 적용 자동화는 이 기획의 완료 조건에 포함하지 않는다.

## 13. 운영 비용과 예산 제어

가격은 특정 제공자에 고정하지 않는다. 비용 모델은 `외부 수집·저장 + LLM 호출 + 사람이 검토한 시간 + 내보내기·실험 지원`으로 나누고, 실제 첫 실행에서 단가·호출 수·검토 시간을 기록한다.

| 비용 항목 | 측정 단위 | 제어 방법 |
| --- | --- | --- |
| 근거 수집 | 요청 수, 바이트, 수집·재시도 시간 | snapshot 재사용, 변경분 수집, 요청 예산 |
| 초기 제안 | 입력/출력 토큰, 호출 수, 지연 | 후보를 먼저 좁히고 공통 맥락·세 대안을 한 실행에서 재사용 |
| 대화 수정 | 수정당 토큰·재시도·검증 시간 | 전체 재생성보다 구조화된 patch, 잠금 보존, 변경 영향만 재검토 |
| 검토 | 근거 검토·역할 확인·최종 승인 시간 | 사람이 확인할 항목과 이미 확인된 항목을 분리 |
| 저장·배포 | 원본/로그/산출물 용량, 보관 기간 | 고객 입력과 공개 데이터의 별도 보관·정리 정책 |

실행마다 토큰·호출 수·최대 재시도·벽시계 시간·금액 예산을 설정한다. 금액은 실행 당시의 단가 또는 내부 환산 단가와 기준일을 기록한 추정이다. 한도에 도달하면 완료한 부분과 검증 미완료 부분을 반환하고 중단한다. 비용 절감을 위해 근거 확인이나 제약 검사를 생략하지 않는다. 자동 재시도는 같은 실패가 반복되지 않도록 횟수를 제한하고, 제공자 실패 시 검증된 마지막 설계와 규칙 검사만 사용해 작업을 재개할 수 있게 한다.

첫 파일럿의 운영 지표는 실행당 비용·지연·수정 횟수, 근거 검토 시간, 사용자 반영률, 미해결 제약 수다. 반영률을 효과나 만족도의 대체 지표로 사용하지 않는다. 품질·실행 가능성·예산을 함께 보고 MVP의 경제성을 판단한다.

## 14. 제품 검증과 완료 기준

검증은 실제 제품을 구현할 때 수행할 계획이며 지금 통과한 결과가 아니다. 자동 판정 가능한 항목과 사람의 판단이 필요한 항목을 나누고 평가 사례·예상 판정·실제 판정·검토 의견을 저장한다.

### 필수 사례

- 유효한 제약 내에서 모듈을 조합하고 모든 참조·역할·경로를 완성한다.
- 충돌하는 모듈, 부족한 역할, 상한 초과, 순환 의존, 존재하지 않는 근거 ID를 검출한다.
- 필수 조건 또는 잠금과 충돌하는 수정은 반영하지 않고 이유를 반환한다.
- 불가능한 입력에는 추천을 보류하고, 모르는 입력은 사실로 바꾸지 않는다.
- 출처에 없는 규칙과 새 결합을 AI 신규 제안으로 표시한다.
- 악의적 지시가 들어 있는 외부 문서를 데이터로만 처리한다.
- 동일한 저장 응답으로 판정·내보내기를 재생하고, 새 모델 호출은 새 실행으로 남긴다.
- 내보내기만 실행한 뒤 외부 상태가 바뀌었다고 표시하지 않는다.

### 품질 게이트

1. 고정 평가 사례에서 필수 제약 위반·잠금 변경·잘못된 근거 참조가 있는 안은 최종 권고 상태로 나갈 수 없다. 이는 배포 게이트이며 관찰 전 “오류율 0%” 실적으로 표현하지 않는다.
2. 모든 권고 모듈은 버전·근거 범주·적용 전제·추가 부담·되돌리기·효과 검증 상태를 갖춘다.
3. 제안서와 구조화된 설계·diff·내보내기의 내용이 일치한다.
4. 검토자가 역할·도입 순서·미확인 조건·예외 경로를 설명할 수 있는지 정해진 검토표로 확인한다.
5. 실제 팀의 적용 효과는 기준선·관찰 기간·동시 변화·반례를 가진 별도 실험으로 평가한다. 제안 품질 통과와 효과 입증을 혼용하지 않는다.

근거 감사와 실행 가능성 검토는 가능하면 다른 사람이 수행한다. 독립 검토자가 없으면 자체 검토만 수행했다는 한계를 명시하고 대외 자문 결과에 같은 상태를 유지한다.

## 15. 사용자 사례: 가상의 7인 제품 팀

**이 사례의 인원·시간·관행·결과는 기능을 설명하기 위한 가정이다. 특정 회사의 실제 워크플로우, 분석 실적, 효과 측정 결과가 아니다.** 아래 모듈 이름은 실제 검토된 카탈로그 항목이 아직 아니다.

팀은 주 1회 릴리스하고, 리뷰 가능한 인원이 3명이며, 리뷰 대기가 문제라고 설명한다. 릴리스 주기는 잠그고, 반복 업무 추가 허용량은 팀 전체 주 2시간으로 입력한다. 모든 변경에 별도 승인 2명이 필요하다는 정책이 있는지는 미확인이다.

AI는 현재 정책 확인을 미해결 항목으로 남기고 다음의 조건부 대안을 제시한다.

| 대안 | 가상 모듈 조합 | 반드시 확인할 점 |
| --- | --- | --- |
| 최소 변경 | 일일 리뷰 분류 담당 역할만 순환 | 분류 담당자가 승인 책임까지 떠안는지, 실제 소요 시간 |
| 균형 | 리뷰 분류 + 위험별 경로 + 설계 설명/PR 연결 | 필수 승인 정책, 위험 분류 책임, 역할 부하와 기준선 |
| 통제 강화 | 균형안 + 고위험 변경의 릴리스 전 점검 | 점검을 수행할 역할, 추가 부담이 허용량을 넘는지 |

서로 다른 공개 프로젝트에서 모듈을 가져오는 경우에도 각 카드에 출처 저장소와 범위를 개별 표시한다. 실제 근거가 없는 이 사례에는 회사명을 붙이지 않는다. 위험 경로의 연결을 AI가 새로 만들었으면 그 부분을 신규 제안으로 표시한다.

팀이 “균형안에서 문서 부담을 줄여줘. 릴리스 주기는 유지해줘”라고 요청하면 AI는 설계 설명이 필요한 변경 범위를 좁히는 patch와 diff를 만들고 역할별 부하를 다시 계산한다. 필수 승인 정책을 확인하기 전에는 승인 수 감소를 반영하지 않는다. 릴리스 주기는 그대로 유지한다.

최종 실험안은 우선 리뷰 분류 역할 한 가지를 적용하고 첫 사람 반응 시간, 담당 역할의 추가 시간, 긴급 변경 경로의 문제를 관찰하도록 제안한다. 기준선이 없으면 먼저 기준선을 수집한다. “리뷰 시간이 30% 감소한다” 같은 수치는 제시하지 않는다. 나머지 모듈은 첫 실험을 검토한 후 순차 적용 후보로 남긴다.

이 사용 흐름의 완료는 **근거와 가정이 구분되고, 정책 충돌을 피하며, 팀이 검토하고 되돌릴 수 있는 실행안을 얻은 상태**다. 팀에 맞는 효과가 검증되었다는 결론은 후속 실험의 결과로만 추가한다.
