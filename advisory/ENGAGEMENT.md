# 자문에 사용하는 절차와 납품 기준

상태: 자문 운영 설계. 실제 고객 인터뷰·외부 검토·적용 성과는 아직 없다. 세 사용 모드 중 자문 또는 함께 사용 모드에서 활용하며, 팀 직접 사용 모드도 같은 점검표를 스스로 적용할 수 있다.

## 1. 진단 범위 합의

대상은 ‘회사의 개발 문화를 평가’하는 일이 아니라, 팀이 정한 문제에 대해 현재 흐름과 개선 대안을 검토하는 일이다. 예: 리뷰 대기, 변경 위험 분류 부재, 잦은 릴리스 준비 누락. 동시에 해결할 핵심 문제는 1~2개로 제한한다.

시작 시 제품·역할·필수 정책·현재 단계·역할 가용성·도구·배포 조건과 기존 지표를 확인한다. 공개 연구 자료만으로 특정 고객 팀의 실제 과정을 안다고 가정하지 않는다. 내부 자료가 없다면 인터뷰 기반 진단임을 표시하고, 요청자가 제공한 규정과 실제 준수 여부를 구분한다.

담당자·검토자·팀 의사결정자, 입력 자료의 사용·보관 범위, 모델 처리 위치, 파일 내보내기 범위, 예상 업무량을 기록한다. 고객 자료는 공개 연구 데이터셋이나 다른 고객의 검색 인덱스에 넣지 않는다.

## 2. 현재 흐름과 병목 가설

현재 단계를 트리거·역할·입출력·대기·예외·완료 조건으로 표현한다. 알려진 사실, 인터뷰 진술, AI가 세운 가설을 각각 표시한다.

병목 후보마다 확인할 사건·표본·기준선과 대안 설명을 둔다. PR 대기가 길어도 리뷰 정책뿐 아니라 변경 크기, 요청 시각, 담당자 가용성, 의도적인 보류가 원인일 수 있다. 자료가 부족하면 ‘추가 확인’이 유효한 진단 결과다.

## 3. 세 가지 설계 대안

| 대안 | 설계 원칙 | 반드시 보여줄 내용 |
| --- | --- | --- |
| 최소 변경 | 기존 역할·도구·절차를 최대한 유지 | 이번에 바꿀 한두 관행, 남는 문제 |
| 균형 | 필요한 선행 기능과 운영 부담을 함께 고려 | 채택·제외 이유, 도입 순서, 상충하는 목표 |
| 통제 강화 | 위험도가 높은 경로의 검증·책임을 명확히 함 | 추가 부담, 실제 위험과의 연결, 과도한 통제 가능성 |

세 대안 모두 필수 제약을 지켜야 한다. ‘최소 변경’이 필수 검증 생략을 뜻하지 않고 ‘통제 강화’가 더 우수한 결과를 뜻하지 않는다. 유효안이 부족하면 조건·역할·정책 중 무엇을 바꾸거나 확인해야 하는지 설명한다.

추천은 출처 모듈, 대상 팀에 맞춘 변형, 새 AI 가설을 구분한다. 다른 회사에서의 관찰을 고객 팀에서의 효과나 개선율로 옮겨 쓰지 않는다.

## 4. 자문 패키지

납품 단위는 특정 팀 프로필·모듈 카탈로그·제안 revision에 고정한다.

1. 한 페이지 결정 요약: 해결할 문제, 추천안, 미해결 조건, 팀이 결정할 사항.
2. 팀 프로필과 현재 흐름: 자료 출처·미확인 값·필수 제약 포함.
3. 진단: 관찰한 사실, 병목 가설, 반례와 확인하지 못한 영역.
4. 대안 비교: 선택·제외 이유, 근거, 예상 부담과 부작용.
5. 현재 대비 diff: 단계·역할·정책·검증·예외 처리의 변경표.
6. 실행 가능한 절차: 담당 역할, 트리거, 완료 조건, 예외·복구 경로.
7. 도입 계획: 선행 기능, 준비 작업, 교육, 담당, 시간 추정 범위.
8. 측정·실험 계획: 기준선·사건 수·관찰 기간·판정·중단 조건.
9. 근거 부록: 관찰 기간, 버전, 출처, 효과·적합성·검토 상태.
10. 검토 기록: 누가 어떤 revision의 어떤 범위를 확인했는지와 잔여 이견.

사람 검토는 문체 수정만으로 완료되지 않는다. 원 근거가 주장을 지지하는지, 역할과 시간 제약을 지키는지, 예외 경로가 작동하는지, 팀이 실제 실행할 수 있는지를 확인해야 한다. 별도 검토자를 확보하지 못하면 AI 초안/작성자 검토 상태로 남긴다.

## 5. 도입 가능성 시험과 효과 관찰

먼저 기준선 2주를 관찰하고, 한두 변경을 2주 이상 시험한다. 최소 사건 수와 연장 조건은 시작 전에 정한다. 예: 관련 변경 10건 미만이면 판단을 보류하고 연장한다. 10건은 작은 시험의 운영 예시이며 통계적 보장 기준이 아니다. 월간 릴리스 팀이라면 충분한 릴리스 주기를 포함하도록 기간을 바꾼다.

처리 시간만 보지 않고 재작업·오류·검증 누락·팀 체감 부담을 함께 본다. 실제 배포·사고 데이터를 확보한 경우에만 해당 운영 지표를 산출한다. 공개 PR 시간으로 배포 성과를 대체하지 않는다. [DORA 공식 측정 안내](https://dora.dev/guides/dora-metrics/), [SPACE 연구 소개](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/)

시험 전후의 변경 규모·업무량·담당 가용성·릴리스 일정 차이를 기록한다. 여러 관행을 동시에 바꾸면 개별 효과는 분리하기 어렵다. 도입 성공, 개선 신호, 결론 부족, 악화·철회로 결과를 나누고 불리한 결과도 보존한다.

필수 검증 누락, 책임 공백 또는 합의한 부담 상한 초과 시 중단·복구한다. 정확한 상한과 예외 권한은 대상 팀이 정한다. 본 연구가 새 규정이나 조직 정책을 대신 정하지 않는다.

## 6. 후속 수정과 지식 환류

파일럿 결과는 팀·기간·모듈 버전과 연결한다. 고객 승인을 받은 비식별·공개 가능한 교훈만 공통 모듈 개선에 반영하며, 비공개 증거는 공개 효과 주장의 근거로 배포하지 않는다.

후속 AI 수정은 수정 부분, 영향 범위와 전체 제약을 다시 검사한다. 이미 사람이 검토한 제안이라도 새 revision은 검토 범위를 갱신한다. 팀이 직접 바꾼 절차를 과거 자문자가 계속 보증하는 것처럼 표시하지 않는다.

자문 완료는 **확인된 입력·검토된 제안·팀의 결정 기록**으로 판정한다. 효과 검증 완료는 사전에 정한 관찰과 판정을 따로 완료했을 때 표시한다. 정량 품질 기준은 [평가 계획](../quality/EVALUATION.md), 필드와 상태는 [입출력 계약](../specs/WORKFLOW_CONTRACTS.md)을 따른다.
