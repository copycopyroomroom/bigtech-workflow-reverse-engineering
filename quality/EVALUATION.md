# 평가와 공개·자문 품질 기준 v0.2

작성일: 2026-10-23 (Asia/Seoul)

상태: **평가 설계. 평가 데이터셋 구축·시스템 구현·성능 측정·외부 검토·현장 실험은 모두 미실시**다. 아래 숫자는 초기 수용 목표와 최소 시험 규모이며, 달성한 성능이 아니다. 데이터와 평가 비용을 확인한 뒤 기준을 변경할 수 있으나, 변경 이유와 이전 기준의 결과를 함께 보존한다.

## 1. 평가 목적과 판정 범위

평가는 두 제품을 구분한다.

1. **공개 기록 분석**: 출처가 보여주는 사실을 정확히 추출하고, 정책·실제 관행·해석·확인 불가를 구분했는가?
2. **워크플로우 조합·수정 제안**: 출처에서 얻은 관행을 대상 팀의 제약에 맞게 구성하고, 충돌·부작용·변경 이유·검증 계획을 설명했는가?

분석 정확도가 높아도 제안한 워크플로우가 대상 팀에 효과적이라는 뜻은 아니다. 추천 품질, 사람의 자문 검토, 실제 적용 효과도 별도 판정한다. "여러 회사의 장점 조합"은 관찰된 관행 중 대상 문제에 맞는 후보를 고른다는 의미로 사용하며, 공개 기록만으로 그 관행의 인과적 효과를 확인했다고 쓰지 않는다.

기능 범위는 [워크플로우 조합 기능](../product/WORKFLOW_COMPOSER.md), 객체·필드·검증 규칙은 [공통 계약](../specs/WORKFLOW_CONTRACTS.md), 표본과 수집 방법은 [분석 프로토콜](../methodology/ANALYSIS_PROTOCOL.md)을 따른다. 이 문서는 시험 구성·평가 분모·수용 기준을 정의한다.

## 2. 근거 수준과 적용 상태를 분리한다

### 근거 수준

| 수준 | 의미 | 허용되는 설명 | 이 수준만으로 허용되지 않는 설명 |
| --- | --- | --- | --- |
| E0 `provenance-only` | 출처·버전·시점이 추적됨 | "이 자료를 수집했다" | 해당 절차가 정책이거나 실제 관행이라는 판단 |
| E1 `source-policy` | 해당 범위의 공식 문서가 절차를 규정함 | "문서에 이 절차가 규정되어 있다" | 실제 준수율, 강제 설정, 조직 전체의 실제 운영 |
| E2 `repeated-observation` | 독립 변경 사례 3개 이상에서 같은 관행을 관찰하고 반례를 검토함 | "이 저장소의 이 기간에 반복 관찰했다" | 다른 팀의 성과 개선, 회사 전체의 공통 관행 |
| E3 `target-pilot` | 식별된 대상 팀에서 사전 계획에 따라 적용·측정함 | "이 팀·이 기간에 이런 결과와 한계가 있었다" | 무작위 실험 없는 인과 단정, 다른 팀의 효과 보장 |

E1 문서와 E2 관찰은 별도 근거를 연결한다. E2를 얻었다고 E1 정책의 존재가 자동으로 확인되지는 않는다. E3는 현장 시험을 수행했다는 범위 표시다. 실패·중단·효과 불명인 실험도 E3 자료일 수 있으며, 성공 배지로 사용하지 않는다. 표본 수만으로 근거 수준을 올리지 않는다.

### 적용·자문 상태

계약의 `transfer_status`, `effect_status`, `advisory_review_status`는 근거 수준과 독립적으로 기록한다. 상태값의 상세 전이 규칙은 공통 계약을 따르며, 평가는 다음 의미를 구별할 수 있어야 한다.

| 축 | 구별해야 하는 상태와 판단 |
| --- | --- |
| 적용 전이 `transfer_status` | `unassessed` 미평가, `conditional` 전제 확인 필요, `eligible` 알려진 팀 제약에 적합, `blocked` 제약상 적용 불가, `trial_supported` 대상 시험에서 적용 가능성 확인을 구별한다. `eligible`은 효과 검증이 아니다. |
| 효과 `effect_status` | `untested` 효과 미시험, `feasibility_tested` 실행 가능성만 확인, `target_trial_supported` 대상 팀의 사전 지표에서 기대 방향을 관찰, `inconclusive` 판단 불가, `contradicted` 기대 효과와 반대 결과를 구별한다. 시험 설계와 혼입 요인의 한계를 병기한다. |
| 자문 검토 `advisory_review_status` | `draft` 초안, `ai_checked` AI·규칙 사전 점검, `human_reviewed` 사람의 검토 완료, `target_trial_reviewed` 대상 팀 시험 결과 검토 완료를 구별한다. 검토자의 독립성·판정·수정 요청·실제 적용 승인은 별도 기록한다. |

예를 들어 E2 근거가 충분한 관행도 대상 팀에 필요한 담당자가 없으면 적용 보류다. 외부 검토가 승인된 제안도 현장 효과가 아직 없으면 효과 미검증이다. E3 자료와 `effect_status: contradicted`는 함께 존재할 수 있다. 한 축의 점수를 다른 축의 부족을 상쇄하는 종합 점수로 합치지 않는다.

## 3. 판정자와 책임

| 판정 수단 | 담당할 수 있는 검증 | 담당할 수 없는 최종 판단 |
| --- | --- | --- |
| 결정론적 검증 | 스키마, 참조 ID, 소스 해시, 고정 표본, 계산 재현, 명시된 하드제약, 불가능한 의존 순환·담당 누락, 변경 금지 영역 회귀 | 출처의 의미, 조직 현실, 새로운 관행의 효과 |
| 모델 judge | 근거 후보 대조, 모순 후보 탐지, 누락 검토 보조, 설명 품질의 사전 평가 | 자기 출력의 정확성 확정, 외부 자문 승인, 현장 효과 입증 |
| 사람 검토 | 근거의 의미·범위, 미확인 처리, 평가 정답 작성, 조직 적합성, 실행·중단 조건의 타당성 | 출처에 없는 비공개 프로세스 또는 실행 전 효과의 확정 |
| 대상 팀 담당자 | 실제 역할·가용 시간·정책·도구 확인, 적용 승인, 실험 운영과 결과 확인 | 다른 조직에 대한 효과 일반화 |

모델 judge 결과에는 모델·버전·프롬프트·입력·판정 이유를 남기고, 생성 모델과 동일한 오류를 공유할 수 있음을 표시한다. 여러 모델의 동의도 사람의 독립 검토를 대체하지 않는다. 결정론적 검증이 실패한 결과를 모델 점수로 통과시키지 않는다.

1인 운영 시 작성자와 검토자의 이해관계를 분리했다고 주장하지 않는다. 일정 간격을 둔 자기 재검토는 `단독 재검토`로 표시한다. 외부 검토자가 확보되지 않으면 분석·추천 결과를 **외부 검토 미확보 초안**으로 공개할 수 있으나, 자문 검토 완료 또는 현장 효과 검증 결과로 표기하지 않는다.

## 4. 개발용 평가와 독립 holdout

개발용 세트는 프롬프트·규칙·스키마 수정에 사용한다. 공개·자문 판정용 holdout은 정답과 기대 동작을 먼저 고정한 뒤 사용한다. 개발용과 holdout을 합친 점수만 발표하지 않는다.

### 최소 평가 세트

아래는 추천 기능의 첫 공개 판정을 위한 최소 구성이다. 6개 저장소의 연구가 아직 끝나지 않았다면 구축한 범위만 `파일럿 평가`로 보고하고, 전체 기준 통과로 선언하지 않는다.

| 세트 | 개발용 | 독립 holdout | 구성과 분모 |
| --- | --- | --- | --- |
| R1 근거 해석 | 주장 60개 | 주장 60개 | 각 세트에서 저장소별 10개. 직접 관찰 4개, 정책 문서 2개, 반복 관찰 2개, 불충분/상충 근거 2개로 구성한다. 마지막 유형은 저장소별 누락 1개·상충 1개를 포함한다. |
| R2 추출 대조 | PR 60개 | PR 60개 | 각 세트에서 저장소별 PR 10개. PR 상태, 생성 시각, 사람 리뷰 존재 여부, 원문 연결 4개 필드를 대조한다. 세트당 기본 분모는 240개 필드다. |
| C1 신규 조합 | 팀 프로필 24개 | 팀 프로필 24개 | 아래 8개 상황군마다 서로 다른 프로필 3개. 프로필당 신규 추천 1개로 출력 24개다. |
| C2 수정 회귀 | 변경 요청 24개 | 변경 요청 24개 | C1 프로필마다 기존 결과와 제약 변경 1개를 묶는다. 수정 출력 24개, 전후 비교쌍 24개다. |
| C3 검증기 결함 주입 | 잘못된 워크플로우 36개 | 잘못된 워크플로우 36개 | 6개 결함군마다 6개. 추가로 정상 워크플로우 12개씩을 두어 잘못된 거부를 확인한다. |

R1은 주장별 `출처로 지지됨 / 반박됨 / 확인 불가`, 허용되는 주장 범위, 필수 근거 목록을 사람이 먼저 라벨링한다. 반복 관찰 주장의 3개 이상 사례는 동일 변경의 후속 PR·백포트를 중복 계수하지 않는다. R2에서 실제 원문으로도 알 수 없는 필드는 정답을 `unknown`으로 고정하고, 비어 있는 값과 구별한다.

C1의 8개 상황군은 ① 소규모·겸직 팀, ② 성장 중인 다중 팀, ③ 외부 기여를 받는 OSS, ④ 승인·감사 제약이 큰 조직, ⑤ 잦은 릴리스와 안정성 요구, ⑥ 레거시·도구 제약, ⑦ 정보 부족으로 보류가 필요한 요청, ⑧ 상충하는 요구·실행 불가능한 요청이다. 각 프로필은 목표·현재 절차·역할·가용 시간·도구·하드/소프트 제약·미확인 값을 명시한다. 회사명 바꾸기만으로 서로 다른 프로필로 세지 않는다.

각 상황군의 세 프로필에 self_service / advisory / hybrid를 하나씩 배정해 세 사용 모드를 각 8개씩 평가한다. 다중 팀 환경도 MVP에서는 그 안의 대상 팀 하나·저장소 하나로 범위를 고정한다. 모드별 검토 상태와 인수인계 기록을 확인하며, 동일 출력에 모드 이름만 붙여 세 기능을 구현했다고 세지 않는다.

C2에는 역할 제거, 가용 시간 축소, 필수 승인 추가, 도구 금지, 목표 가중치 변경, 보존할 단계 지정이 각각 4쌍씩 포함된다. 변경을 적용하려면 다른 하드제약이 깨지는 경우는 보류와 이유 설명이 정답이다.

C3의 결함군은 ① 필수 단계/역할 누락, ② 가용 인원·시간 초과, ③ 금지 도구·정책 위반, ④ 불가능한 선행 관계·순환, ⑤ 필수 근거 참조/출처 범위 오류, ⑥ 수정 금지 영역 훼손이다. 하드제약으로 명시하지 않은 취향을 검증기가 임의로 하드제약화하지 않는지도 정상 사례로 확인한다.

재작업처럼 종료·상향 보고 조건이 있는 정상 루프는 허용한다. S1 외부 콘텐츠 경계 시험도 개발용 12개·holdout 12개를 별도로 구성한다. 지시문 삽입·가짜 출처/정답 삽입·기밀 반출 유도 각 4개로 나누고, 격리·무단 도구 실행 없음·출처 허위 생성 없음 12/12를 목표로 한다. 단일 시험 통과를 완전 방어로 설명하지 않는다.

### 분리와 오염 방지

1. R1/R2는 연결된 이슈·PR·백포트·동일 변경 계열을 묶어 한쪽 세트에만 배정한다. 같은 PR의 다른 문장을 양쪽에 나누지 않는다. 동일 정책 문서의 사실상 같은 주장을 중복 평가 항목으로 만들지 않는다.
2. C1/C2는 같은 팀 프로필과 수정 계열을 한쪽에만 둔다. 개발용 프로필의 인원·이름만 바꾼 사례를 holdout으로 사용하지 않는다.
3. 각 세트의 ID·내용 해시·출처 snapshot·기대 답·버전·분리 기준을 freeze manifest에 남긴다. holdout 정답을 추천 입력 또는 검색용 패턴 저장소에 넣지 않는다. 평가 대상의 공개 원문을 입력으로 제공하는 것은 허용하며, 정답 라벨을 숨기는 것과 구분한다.
4. holdout을 보고 프롬프트·규칙을 바꾼 경우 그 세트는 이후 회귀 세트다. 새로운 독립 holdout을 마련하기 전에는 독립 성능 향상을 주장하지 않는다.
5. 동일 6개 저장소에서 만든 holdout은 새로운 회사·분야 일반화 시험이 아니다. 합성 팀 프로필 통과는 실제 조직의 적용 성공이 아니다.

개발용 PR 20개로 먼저 codebook의 정의·경계 사례·`unknown` 처리 규칙을 보정한다. 실제 상세 표본의 독립 코딩 검토는 저장소별 실제 수의 20%를 올림한 수로 한다(각 50개·총 300개 확보 시 저장소별 10개·총 60개). R1 holdout에서는 별도로 최소 12개 주장(20%)을 외부 검토자와 작성자가 서로의 라벨을 보지 않고 독립 분류한 뒤 불일치를 기록·해결한다. 이 세 작업은 목적과 분모가 다르며 같은 작업으로 합산하지 않는다. 합의 전 일치율과 불일치 수를 함께 남긴다. 외부 참여자가 없으면 독립 검증은 미실시이며 자문 gate를 통과할 수 없다.

이 평가 세트와 교차 코딩은 기존 연구 표본 300개와 별도 작업량을 만든다. 첫 개발용 10개에서 항목당 라벨 작성·분류·외부 검토 시간을 측정하고 전체 비용을 추정한다. 예산을 넘으면 공개 단계·범위를 줄이거나 일정을 늘리고, 최소 평가 규모를 채운 것처럼 표시하지 않는다.

| 항목 | 분자 / 분모 | 초기 수용 목표 | 판정 |

| 출처 추적 | 유효한 소스 ID·버전·시점·직접 위치를 모두 가진 주장 / R1 주장 60개 | 60/60. 하나라도 없는 핵심 주장은 공개 보류 | 결정론 검증 + 사람의 직접 열람 |
| 근거 일치 | 정답의 지지/반박/확인 불가와 의미·범위가 일치한 주장 / R1 60개 | 57/60 이상, 중대한 허위 단정 0건 | 사람. 모델은 검토 보조 |
| 정책·관행 구분 | 정책을 실제 준수로 오인하지 않은 판정 / R1 정책 12개 | 12/12 | 사람 |

중대한 허위 단정에는 원문에 없는 필수 승인·강제 정책 단정, 비공개 과정의 부재 단정, 저장소 관찰의 회사 전체 일반화, 공개 PR 지표를 실제 배포·장애 효과로 바꾸는 행위를 포함한다. 이런 결함은 평균 정확도가 목표 이상이어도 해당 보고서를 보류한다.

전체 PR 목록의 완전성은 R1/R2 정답 정확도와 별도다. `성공 수집 수 / 예상 총수 / 실패 요청 수 / unknown 수`를 저장소별로 보고한다. 예상 총수를 확정할 수 없으면 수집률을 억지로 계산하지 않고 `분모 미확정`으로 쓴다. 불완전한 기본 목록을 전체 모집단 통계로 발표하지 않는다.

## 6. AI 조합·수정 평가

품질 분모는 holdout C1 24개 + C2 24개 = **총 48개 응답**이다. 이 문서에서 출력 1개는 응답 1개를 뜻한다. 응답에 최소 변경·균형·통제 강화 대안이 함께 있으면 포함된 대안을 모두 검사하며, 한 대안의 제약 위반도 그 응답의 실패다. 대안 단위 결과와 실제 대안 수도 별도로 보고한다. 실행 불가 대안은 이유와 보류 상태를 표시하고 실행안으로 발행하지 않는다.

생성 실패·시간 초과·스키마 오류도 48개 중 실패로 포함한다. 정답이 보류/추가 정보 요청인 상황은 올바른 보류로 통과할 수 있으나, "추천을 제공한 비율"과 분리한다.

| 항목 | 측정·분모 | 초기 수용 목표 | 판정 |
| --- | --- | --- | --- |
| 형식·참조 무결성 | 스키마와 존재하는 패턴·주장 참조를 만족한 출력 / 48개 | 48/48 | 결정론 |
| 하드제약 | 명시된 모든 하드제약을 만족하거나 실행안 발행을 보류한 출력 / 48개. 별도로 통과 제약 수 / 전체 제약 수 병기 | 출력 단위 48/48, 제약 단위 100% 목표 | 결정론, 현실성은 사람 확인 |
| 충돌 검출 | 기대 충돌을 빠짐없이 보고한 출력 / 충돌 정답이 있는 출력 수 | 100%. 충돌 사례 수를 manifest에서 먼저 고정 | 결정론 + 사람 |
| 역할·가용성 | 담당·대리·결정권과 가용 인원/시간 안에서 실행 가능한 출력 / 48개 | 48/48 또는 명시적 보류 | 결정론 + 대상 맥락을 읽는 사람 |
| 근거 귀속 | 원 출처와 범위에 맞게 서술한 외부 관행 주장 / 48개 출력 안의 모든 외부 관행 주장 수 | 출처 없는 핵심 귀속 0건, 중대한 왜곡 0건. 실제 분모·일치율도 보고 | 사람. 단순 URL 존재 검사로 대체하지 않음 |
| 정보 부족 처리 | 필요한 질문·미확인 가정·보류를 정확히 처리한 출력 / 정보 부족 정답이 있는 출력 수 | 100% | 사람 |
| 수정 회귀 | 요청 변경 반영·유지 제약 보존·부작용 설명이 모두 맞는 비교쌍 / C2 24쌍 | 24/24. 의미 변경 없는 새 ID 발급도 추적 오류로 기록 | 결정론 diff + 사람 |
| 자문 정합성 | 아래 모든 항목이 각각 3점 이상인 출력 / 48개 | 외부 검토 완료 범위에서 48/48. 미검토는 통과로 세지 않음 | 사람 |
| 과도한 보류 | 기대 답이 실행 가능한 제안인 상황에서 불필요하게 보류한 출력 / 실행 가능 정답 출력 수 | 10% 이하. 어려운 문제를 모두 거부해 제약 점수를 높이는지 확인 | 사람 |

**100% 하드제약 통과는 달성 목표이며 현재 성능이 아니다.** 한 건이라도 위반하면 해당 버전의 자동 실행안 발행을 보류한다. 실패한 결과를 사람이 수정한 뒤 AI 원출력이 통과했다고 재계산하지 않는다. 수정 전·후와 수정 주체를 각각 기록한다. 미확인 정책·가용성은 통과가 아니라 추가 확인이 필요한 상태다.

검증기 자체는 C3에서 결함 36/36을 검출하고 정상 12/12를 수용해야 한다. 알려진 결함만 통과한 것이므로 보편적 안전 보장으로 표현하지 않는다. C3를 통과해도 C1/C2의 의미 평가를 생략하지 않는다.

### 사람의 자문 정합성 루브릭

각 출력에 대해 1점(실행 불가/핵심 결함), 2점(중요 수정 필요), 3점(조건 명시 후 시험 가능), 4점(명확하고 실행·검증 가능)으로 판정하고 이유를 적는다.

1. 대상 문제·우선순위와 단계·관행 사이의 연결.
2. 팀 규모·역할·도구·가용 시간에 맞는 실행 가능성.
3. 다른 출처의 관행 사이 선행 조건과 충돌의 해소.
4. 원 관행·AI가 바꾼 요소·가정·불확실성의 구별.
5. 추가 운영 부담·실패 위험·대안과 선택 이유의 설명.
6. 기준선·측정값·담당자·중단/복구 조건을 가진 적용 실험안.
7. 대안별 변경 범위·운영 부담·통제 수준의 실질적 차이와 선택 이유. 이름만 다른 동일안으로 선택지가 늘어난 것처럼 보이지 않는가?

평균 점수로 핵심 결함을 숨기지 않는다. 어느 항목이든 3점 미만이면 해당 제안은 수정 요청이다. 최소 1명의 외부 검토자는 리뷰·릴리스·개발 프로세스 운영 경험이 있어야 하며, 역할과 이해관계를 공개한다. 대상 팀이 있다면 그 팀의 담당자가 실제 가용성과 정책을 별도로 확인해야 한다. 외부 검토자와 대상 팀 담당자는 가능하면 다른 사람으로 확보하고 겸임한 경우 제한을 밝힌다.

## 7. 비교 기준선·요소 제거 실험

완성 시스템의 설명이 설득력 있다는 이유만으로 개선이라고 판단하지 않는다. 동일한 holdout C1 24개에서 다음 버전을 같은 모델·출력 한도·입력 정보·실행 시점 조건으로 비교한다.

| 버전 | 구성 | 확인할 질문 |
| --- | --- | --- |
| B0 | 팀 프로필과 일반 프롬프트만 제공하는 모델 | 근거·구조가 없는 일반 제안 대비 이점이 있는가? |
| B1 | 출처를 연결한 패턴 검색·제안을 제공하되 조합 규칙은 제외 | 근거 연결만으로 얼마나 개선되는가? |
| B2 | 패턴과 조합을 제공하되 명시적 제약·충돌 검증은 제외 | 검증기가 어떤 오류를 줄이는가? |
| F | 패턴·팀 프로필·조합·검증·설명을 모두 사용 | 전체 기능의 추가 비용이 품질 차이에 상응하는가? |

네 버전 모두 원출력을 평가한다. 불완전한 B0 결과를 평가자가 임의로 구조화한 뒤 정상이었다고 처리하지 않는다. 공통 의미 지표를 비교하고, 스키마가 없는 버전은 구조 위반을 별도 보고한다. 판정자는 가능한 범위에서 버전명을 보지 않고 순서를 섞어 검토한다. 차이의 원인이 여러 요소에 걸친 경우 특정 요소의 인과적 효과라고 주장하지 않는다.

C2의 24쌍에서는 전체 재생성 방식과 변경 범위를 보존하는 수정 방식도 비교한다. 올바른 수정 비율, 유지 제약 훼손, 변경 단계 수, 비용을 함께 보고한다. 기준선 비교는 주장한 개선 범위에만 사용하며, 표본이 작으므로 회사·업종별 우열을 만들지 않는다.

반복 안정성은 holdout의 상황군별 1개 프로필, 총 8개에서 신규·수정 각각 3회 추가 실행한다(8 × 2 × 3 = 48개 출력). 최초 48개 평가와 별도 표로 보고한다. 동일 입력에서 제약 위반·결정 상태·주요 구조가 얼마나 달라지는지 확인하며, 반복 실행 결과 중 가장 좋은 것만 고르지 않는다.

## 8. 시간·비용·운영 부담

모든 실행은 `run_id`, 데이터/패턴/계약 버전, 모델 제공자·모델 버전, 프롬프트 해시, 파라미터, 도구 호출, 재시도, 입력/출력 토큰, 캐시, 오류, 시작/종료 시각을 기록한다. 비용 계산의 요율과 확인 일자도 보존한다. 비밀정보와 인증 토큰은 기록하지 않는다.

| 비용·성능 지표 | 보고 방법 |
| --- | --- |
| 수집 비용 | 저장소별 요청 수·전송량·총 경과 시간·재시도·권한/속도 제한·저장 용량 |
| 추천 지연 | 최초 사용자 입력부터 검증 완료까지 중앙값·p95·최댓값. 실패/보류 수 병기, 성공 출력만의 지연도 구분 |
| 추천 비용 | 전체 요청당 비용, 성공 추천당 비용, 보류/실패 비용. 모델·검색·재시도·검증 호출을 포함 |
| 수정 비용 | 최초 생성과 수정의 토큰·도구 호출·경과 시간·사람 검토 시간 비교 |
| 사람 검토 | 주장 또는 제안당 검토 분·수정 횟수·평가자 불일치. 무료 노동으로 가정하지 않음 |
| 팀 운영 부담 | 제안 도입 후 주간 추가 회의·리뷰·담당 시간과 일회성 설정 시간. 추정값과 실제값 분리 |

시스템 지연·비용 예산은 초기 10개 개발용 실행 후 제품 요구와 가용 예산에 맞게 freeze한다. 동결 전에는 `목표 미확정`이며 비용 수용 gate가 미완료다. 결과를 본 뒤 예산을 조정하면 이전 목표의 초과도 보존한다. 24개처럼 작은 표본의 p95는 탐색 통계이며 운영 SLA로 광고하지 않는다.

## 9. 공개·자문 gate

OSS self-service, advisory workbench, hybrid는 선택 가능한 사용 모드이며 우선순위를 정하지 않는다. 아래 gate는 주장할 수 있는 품질·검토 상태를 제한한다. OSS 연구·실험 기능은 현재 상태와 한계를 표시하여 공개할 수 있고, G3/G4는 자문 검토 완료·현장 검증을 주장하려는 범위에 적용한다. 최소 변경·균형·통제 강화는 추천 대안의 종류이며 사용 모드와 구분한다.

| 단계 | 필요한 증거 | 허용되는 결과 상태 |
| --- | --- | --- |
| G0 계획·설계 | 요구사항·계약·평가 계획, 측정 미실시 표시 | 계획서·시제품 설계 |
| G1 재현 가능한 연구 | 수집 완전성/누락 보고, R1/R2·재현 목표 통과, 모든 핵심 주장 출처 감사 | 한계를 밝힌 연구 보고서. 외부 검토 미확보 시 초안 표시 |
| G2 조합 기능 평가 | G1 + C1/C2/C3/S1 목표·기준선·비용 평가, 하드제약 위반 0건, 실패·보류 공개 | 적용 효과 미검증인 워크플로우 제안 기능. 외부 검토 미확보로 사람 평가가 미완료면 G2 통과도 미완료이며, 그 상태를 표시한 실험 도구 공개만 가능 |
| G3 자문 검토 완료 | G2 + 독립 라벨 점검 + 외부 전문가의 제안별 검토 승인 + 대상 팀의 조건 확인·실험 계획 승인 | 검토된 적용 실험 제안, `human_reviewed`. 모델 단독 judge로 통과 불가 |
| G4 대상 팀 실험 결과 | 사전 기준선·실행 기록·중단/복구 기록·성과/부작용·팀 확인·사람의 결과 검토 | 해당 팀·기간의 결과 보고, `target_trial_reviewed`. E3와 `effect_status`를 함께 표시 |

일부 제안만 검토되면 승인 범위도 그 제안으로 한정한다. 시스템의 G2 평가 통과가 미래의 모든 추천에 대한 G3 승인인 것처럼 표현하지 않는다. 실제 사용 시 새 대상 프로필·새 추천도 개별 검증과 검토를 거친다.

G4는 필수적으로 "개선 성공"을 요구하지 않는다. 기간이 짧거나 변경량이 적어 결론이 안 나면 `판단 불가`로 보고한다. 인과 주장은 별도 설계가 없는 한 하지 않는다. 대상 팀이 없으면 G4는 미착수로 남기며, 합성 프로필을 현장 실험으로 대체하지 않는다.

## 10. 결과표와 변경 관리

결과 보고서는 최소 다음 표를 포함한다.

| 평가 대상 | 세트/버전 | 실제 분자/분모 | 누락·실패·보류 | 판정자 | 수용 기준 | 상태 |
| --- | --- | --- | --- | --- | --- | --- |
| 근거 일치 | 미구축 | — / — | 미측정 | 미배정 | R1 57/60 이상, 중대 오류 0 | 미실시 |
| 하드제약 | 미구축 | — / — | 미측정 | 미배정 | 출력 48/48 및 제약 100% | 미실시 |
| 수정 회귀 | 미구축 | — / — | 미측정 | 미배정 | 24/24 | 미실시 |
| 외부 자문 검토 | 미확보 | — / — | 미검토 | 미배정 | 항목별 3점 이상, 제안별 승인 | 미실시 |
| 비용·지연 | 미구현 | — / — | 미측정 | 미배정 | 초기 측정 후 예산 동결 | 미실시 |
| 대상 팀 적용 | 대상 미확정 | — / — | 미착수 | 미배정 | 사전 실험 계획에 따름 | 미실시 |

`0/0`을 100%로 표시하지 않는다. 해당 사례가 없으면 미평가 또는 적용 대상 없음으로 구분한다. 최소 시험 구성에서 필수 유형이 빠지면 해당 gate는 미완료다. 수용 판정은 개발용/holdout·원출력/사람 수정·독립 검토/자기 검토를 분리한다.

모델·프롬프트·검색 방식·패턴 내용·제약 규칙·계약 의미가 바뀌면 영향받는 평가와 전체 하드제약 회귀를 다시 실행한다. 원본 스냅샷이 바뀌면 연구 지표의 재계산과 출처 범위도 점검한다. 단순 문구 교정은 의미·스키마·판정 기준을 바꾸지 않았음을 확인하면 전체 모델 평가를 재실행하지 않아도 된다.

실패 기록에는 재현 입력, 기대 동작, 실제 동작, 영향 범위, 원인 가설, 수정 버전, 재평가 결과를 남긴다. 계획 기준을 만족하지 못했다고 실패 사례를 세트에서 삭제하지 않는다. 실제 오류인 정답 라벨은 수정 이유·이전 결과·수정 결과를 함께 공개한다.

첫 실행 순서는 **개발용 소규모 표본으로 수집·검증기를 확인 → 평가 라벨과 비용 예산 고정 → 독립 holdout 구성 → 원출력 평가 → 외부 검토 → 대상 팀 실험**이다. 현재 프로젝트는 G0 설계 단계이며 G1 이후의 실적은 없다.

## 11. 웹 플랫폼의 추가 출시 조건

위 연구·추천 평가는 [플랫폼 구현 설계](../architecture/PLATFORM.md)의 인증·고객 격리·파일 접근·워커 복구·동시 예산·revision·접근성·백업 복구 시험을 대체하지 않는다. 플랫폼 P1은 localhost 단독 사용자 실험으로 제한하고, 다중 사용자·고객 호스팅은 해당 조건을 별도로 통과한 범위에서 제공한다. 플랫폼 구현과 운영 시험도 아직 미실시다.
