# 분석 프로토콜 v0.1

작성일: 2026-10-23

상태: 첫 수집 전에 검증할 설계. 수집 도구는 아직 구현되지 않았다.

## 1. 분석 단위와 관찰 범위

기본 단위는 `저장소 × 생성 기간 × 관찰 종료 시점`이다. 공개 기록으로 확인되는 팀 단위의 과정만 설명한다. 개인별 성과·고용 관계·근무 시간은 추정하지 않는다.

공통 PR 생성 기간은 `[2026-07-01T00:00:00Z, 2026-10-01T00:00:00Z)`다. 본 수집 시작 시각을 모든 대상의 `snapshot_utc`로 고정한다. 수집 요청별 `fetched_at_utc`도 저장한다.

API 응답은 여러 시각에 받아지므로 원자적인 과거 스냅샷으로 간주하지 않는다. `snapshot_utc` 이후 이벤트는 분석에서 제외하고, `merged_at`·종료·재개 이벤트로 종료 시점 상태를 재구성한다. 과거의 본문·라벨·diff·권한을 재구성할 수 없으면 수집 당시 값임을 표시하고 과거 시점 주장에 쓰지 않는다. 재구성이 불가능한 상태는 `unknown`으로 둔다.

기간 변경이 필요하면 원래 공통 기간 분석과 별도 결과로 남긴다. 문서는 가능하면 해당 기간의 커밋 SHA에 고정하며, 현재 문서만 확인했으면 현재의 규정이라고 표시한다.

## 2. 원본과 정규화 자료

| 자료 | 최소 필드 | 용도·한계 |
| --- | --- | --- |
| 저장소 | ID, 정식 이름, URL, 기본 브랜치, 보관 여부, 확인 시각 | 이전·이름 변경을 추적 |
| PR | ID/번호, URL, 생성·draft/ready·병합·종료 시각, head/base SHA, 변경량, 파일 수 | 생성 당시 변경량과 최종 변경량을 구분. 복원 불가 시 최종값으로 명시 |
| 리뷰 | ID, PR, 제출 시각, 상태, 작성자 역할 구분, commit SHA | 승인·변경 요청·코멘트 및 승인 취소 이벤트를 구분 |
| 대화·타임라인 | ID, 유형, 시각, 작성자 구분, 연결 URL | 일반 코멘트와 코드 리뷰 코멘트, 봇과 사람을 분리 |
| CI | head/검증 SHA, check run·status 이름, 시작·종료·결론, 조회 시각 | 이전 실행의 미보존·비공개·권한 부족과 실제 실패를 구분 |
| 커밋·릴리스 | SHA, 태그, 공개 시각, PR 연결, 연결 방법 | 태그 포함 관계와 릴리스 노트의 언급을 구분 |
| 절차 문서 | URL, 커밋 SHA 또는 내용 해시, 확인 시각, 적용 범위 | 현재 규정과 과거 실제 운영을 구분 |

인물 식별자는 작성자 본인·다른 사람·봇과 같은 역할 판정에 필요한 범위만 보존한다. 외부 공개 결과는 집계와 사건별 출처 링크 중심으로 작성하고, 개인 순위나 개인별 처리 시간을 만들지 않는다.

## 3. 수집과 완전성 확인

1. 저장소 ID와 정식 URL을 확정한다. 이동 전후 URL을 중복 저장소로 세지 않는다.
2. REST 또는 GraphQL로 생성 기간의 PR 목록을 수집한다. 검색 API를 쓰면 기간을 작은 구간으로 나누고 페이지를 끝까지 읽는다.
3. GitHub 검색은 검색당 최대 1,000개 결과를 제공하므로 구간별 건수를 확인하고 필요하면 재분할한다. `incomplete_results`와 실제 수집 건수도 확인한다. [공식 검색 API 문서](https://docs.github.com/en/rest/search/search)
4. 리뷰·리뷰 코멘트·일반 코멘트·타임라인 등 중첩 목록도 각각 페이지네이션한다. 첫 페이지만 받아 완료 처리하지 않는다. [공식 페이지네이션 문서](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)
5. 기본 목록을 확보한 뒤 표본 PR의 상세 자료를 가져온다. CI는 check runs와 commit statuses 등 해당 프로젝트가 노출한 경로를 확인한다. [Check runs API](https://docs.github.com/en/rest/checks/runs)
6. 속도 제한·권한·일시 오류를 구분하고, 재시도·대기·재개 위치를 기록한다. 수집량은 첫 주 점검 결과로 추정한다. [공식 속도 제한 문서](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
7. 저장소별 10건을 웹 화면과 대조한다. PR 상태·리뷰·주요 시각·연결을 확인하고 불일치 원인을 기록한다.

인증이 필요하면 공개 데이터 읽기에 필요한 최소 범위의 인증만 사용한다. 토큰은 환경변수로 주입하고 파일·로그에 남기지 않는다. 기본 목록이 불완전하면 전체 건수 기반 지표는 잠정 또는 산출 불가로 표시한다.

manifest에는 `run_id`, 프로토콜 버전, 코드 버전, 저장소 ID, 생성 기간, `snapshot_utc`, 수집 시작·종료 시각, 요청 설정·페이지 수, 수집·실패 건수, 원본 파일 해시, 실행 명령, 누락과 재시도 기록을 남긴다. 원본을 다시 불러오는 것은 나중의 새 수집이고, 기존 원본을 재분석하는 것과 구분한다.

## 4. 표본과 사례 선정

### 기본 목록과 상세 표본

기본 목록은 생성 기간의 모든 PR을 목표로 한다. 봇·자동 생성·사람·불명확을 분류한 후, 사람 작성 PR에서 저장소별 최대 50개를 추출한다. 상태는 추출 조건으로 쓰지 않는다.

고정 규칙은 각 PR에 대해 `SHA256("btw-v1:2026Q3:" + repository_id + ":" + pr_number)`를 계산하고, 해시 오름차순으로 앞 50개를 고르는 것이다. 문자열 인코딩은 UTF-8, ID와 번호는 10진 문자열로 고정한다. 해시 충돌 시 PR 번호 오름차순으로 정렬한다. 실제 구현 시 고정 원본을 이용한 재현 확인을 수행한다.

사람 작성 PR이 50개 미만이면 전수 포함하고 부족분을 기록한다. 자동 생성 여부는 계정 유형, 프로젝트가 문서화한 자동화 계정, PR의 명시적 생성 표시로 판정하며, 이름만으로 불확실한 것은 `unknown`으로 남긴다. 분류 규칙과 수동 수정 내역을 버전 관리한다.

관찰 종료 시 열린 PR·병합 PR·병합 없이 닫힌 PR을 함께 보존한다. 표본에서 특정 상태가 드물어도 결과에 맞춰 표본을 다시 뽑지 않는다.

### 심층 사례

저장소별 PR 사례 6개는 기능·버그 수정·유지보수·설계 논쟁·미병합·회귀 대응을 가능한 범위에서 포함한다. 이 여섯 유형은 탐색 관점이며 서로 배타적인 통계 분류가 아니다. 별도로 설계 또는 릴리스 자료 2개를 확인한다.

선정 이유, 상세 표본 포함 여부, 부족한 유형을 남긴다. 표본 밖에서 보완한 사례는 보완 사례라고 표시하고 통계에서 제외한다. 흥미로운 사례만으로 해당 관행의 보편성을 주장하지 않는다.

## 5. 1차 지표

| 지표 | 계산 | 분모·해석 |
| --- | --- | --- |
| PR 생성량과 자동화 비중 | 전체 건수, 봇·사람·불명확 건수 | 기본 목록. 개발 생산성이나 팀 규모로 해석하지 않음 |
| 상태 분포 | 종료 시점 병합·미병합 종료·열림·불명확 수 | 기본 목록. 작성자 유형별로 나눔 |
| 첫 사람 반응 시간 | 생성 후 첫 비작성자 사람의 코멘트/리뷰까지의 시간 | 상세 표본. 봇·작성자 반응 제외, 무반응 수 별도 표시 |
| 첫 공식 리뷰 시간 | 생성 후 첫 비작성자 사람의 제출된 리뷰까지의 시간 | 일반 대화와 분리, draft 포함 시간을 기본으로 표시 |
| 준비 이후 첫 반응 시간 | 최초 ready 시점 이후 첫 비작성자 사람의 반응까지의 시간 | ready 이력 확인 가능 PR만 보조 지표로 산출. 그전에만 반응이 있던 PR은 별도 표시 |
| 병합 소요 시간 | 생성→병합 시간의 중앙값·분포 | 관찰 종료까지 병합된 사람 PR만. 병합 표본 수와 열린 PR의 경과 시간을 병기 |
| 변경 규모 | 변경 파일 수, 추가·삭제 줄 수의 중앙값·분포 | 상세 표본의 값과 측정 시점 표시. 생성 파일·vendor 영향 기록 |
| 공개 리뷰 흔적 비율 | 병합 전 사람 리뷰/대화가 확인된 PR 비율 | 병합 PR 상세 표본. 공식 리뷰와 일반 대화 비율을 구분 |
| 테스트 변경 동반 비율 | 코드 변경 PR 중 관련 테스트 변경이 확인된 비율 | 상세 표본의 코드 변경 PR. 파일명 휴리스틱을 수동 점검 |
| 공개 CI 관찰 범위 | 성공·실패·대기·취소·누락·불명확 분포 | 조회한 SHA와 시점을 명시. 병합 당시 검증이 복원된 사례만 그 시점 지표에 사용 |
| 릴리스 연결 범위 | 포함 태그가 검증된 PR, 노트 언급만 확인된 PR, 미확인 수 | 연결 방법별로 분리. 제품 배포 시각으로 해석하지 않음 |

시간은 달력 시간 기준 UTC로 계산한다. 국가·근무 시간대 추정은 하지 않는다. 각 결과에 `대상 수 / 해당 분모 / 누락 수`를 표시한다. 무반응·미병합 PR을 0시간으로 넣거나 제거해 전체가 빠른 것처럼 계산하지 않는다.

50개 상세 표본은 탐색용이다. 꼬리 분위수와 세부 집단 순위는 피하고, 작은 집단은 건수와 사례 중심으로 제시한다. 전체 분포를 보여줄 때도 언어·변경 규모·봇 비중·공개 범위의 차이를 함께 설명한다.

첫 단계에서는 리뷰 왕복 횟수, 결함 유발률, 배포 빈도, 장애 복구 시간, 개인 생산성은 산출하지 않는다. 공개 PR의 왕복과 실제 작업 단위를 연결하거나 운영 장애와 배포 시점을 확인할 근거가 먼저 필요하다.

## 6. 사실·해석·적용 제안

모든 핵심 주장에는 ID를 붙이고 다음 항목을 연결한다.

| 항목 | 내용 |
| --- | --- |
| observation | 직접 관찰한 사실. URL, 사건 시각, 수집 시각, 문서 버전 |
| interpretation | 관찰을 설명하는 해석과 다른 가능한 설명 |
| scope | 적용되는 저장소·기간·변경 유형·표본 수 |
| counterevidence | 맞지 않는 사례, 누락, 공개되지 않은 과정 |
| confidence | 높음·중간·낮음과 그 이유 |
| application | 다른 팀에 제안할 실험과 전제 조건 |

반복된 관행이라는 주장은 최소 3개 독립 변경 사례를 출발 기준으로 삼고 반례를 찾는다. 3개는 통계적 유의성이나 높은 신뢰도를 보장하지 않는다. 정책 문서의 규정과 실제 준수는 서로 다른 주장으로 남긴다. 문서 한 건으로 확인한 사실은 문서 사실로 기술할 수 있다.

회사 간 우열, 빠른 병합이 높은 품질을 만든다는 인과관계, 코멘트 수가 많은 리뷰가 좋은 리뷰라는 평가는 하지 않는다. 한 카테고리당 한 저장소인 1차 연구에서는 회사 효과와 분야 효과를 분리할 수 없음을 보고서에 명시한다.

## 7. 재현·검증과 적용 실험

첫 수집기 검증은 10개 PR의 화면 대조, 중첩 페이지 누락 확인, 동일 원본의 중복 제거·표본 재추출·지표 일치 확인에 집중한다. 수집 도구를 구현할 때에는 실제 실패 위험이 있는 페이지네이션, 종료 시점 상태 재구성, 시간 필드 누락을 검증한다.

분석 완료 후 표본 일부를 일정 간격을 두고 다시 분류한다. 다른 검토자가 참여하면 일부를 독립 분류하여 차이와 합의 기준을 남긴다. 참여자가 없으면 단독 연구의 한계라고 표시한다.

플레이북의 효과는 대상 팀에서 별도 검증한다. 실험마다 문제, 변경할 관행 하나, 사전 기준선, 2주 관찰 지표, 담당 역할, 추가 업무량, 중단 조건을 정한다. 팀의 기준선이 없으면 먼저 기준선을 수집한다. 보고서 완료와 실제 팀에서의 효과 검증은 별도 단계다.
