# 분석 프로토콜 v0.2

작성일: 2026-10-23

상태: 연구·제품 설계 명세. 수집기, AI 추출기, 조합 엔진과 평가 도구는 아직 구현되지 않았으며, 분석 결과나 효과 검증을 완료한 상태가 아니다.

이 문서는 공개 기록을 근거와 패턴으로 만드는 방법을 정의한다. 패턴·팀 프로필·추천안의 공통 필드와 상태는 [워크플로우 계약](../specs/WORKFLOW_CONTRACTS.md), 제품 평가와 출시 게이트는 [평가 계획](../quality/EVALUATION.md)을 따른다. 사용 방식은 OSS 자가 사용, 자문 워크벤치, 혼합 사용 모두를 지원하며 어느 방식도 이 프로토콜만으로 전문가 검토나 효과 검증을 완료한 것으로 간주하지 않는다.

## 1. 분석 단위와 관찰 범위

기본 단위는 `저장소 × 생성 기간 × 관찰 종료 시점`이다. 공개 기록으로 확인되는 팀 단위의 과정만 설명한다. 개인별 성과·고용 관계·근무 시간은 추정하지 않는다.

공통 PR 생성 기간은 `[2026-07-01T00:00:00Z, 2026-10-01T00:00:00Z)`다. 본 수집 시작 시각을 모든 대상의 `snapshot_utc`로 고정한다. 수집 요청별 `fetched_at_utc`도 저장한다.

API 응답은 여러 시각에 받아지므로 원자적인 과거 스냅샷으로 간주하지 않는다. `snapshot_utc` 이후 이벤트는 분석에서 제외하고, `merged_at`·종료·재개 이벤트로 종료 시점 상태를 재구성한다. 과거의 본문·라벨·diff·권한을 재구성할 수 없으면 수집 당시 값임을 표시하고 과거 시점 주장에 쓰지 않는다. 재구성이 불가능한 상태는 `unknown`으로 둔다.

기간 변경이 필요하면 원래 공통 기간 분석과 별도 결과로 남긴다. 문서는 가능하면 해당 기간의 커밋 SHA에 고정하며, 현재 문서만 확인했으면 현재의 규정이라고 표시한다.

첫 6개 저장소는 분야를 균형 있게 탐색하기 위한 의도적 사례 선정이다. 빅테크 전체, 회사 전체, 모든 개발팀의 대표 표본이라고 주장하지 않는다. PR의 모집단은 해당 저장소와 생성 기간의 공개 기록으로 한정한다. 저장소 선정 과정의 편향과 그 안에서 PR을 추출하는 과정의 편향을 따로 설명한다.

## 2. 원본과 정규화 자료

| 자료 | 최소 필드 | 용도·한계 |
| --- | --- | --- |
| 저장소 | ID, 정식 이름, URL, 기본 브랜치, 보관 여부, 확인 시각 | 이전·이름 변경을 추적 |
| PR | ID/번호, URL, 생성·draft/ready·병합·종료 시각, head/base SHA, 변경량, 파일 수 | 생성 당시 변경량과 최종 변경량을 구분. 복원 불가 시 최종값으로 명시 |
| 리뷰 | ID, PR, 제출 시각, 상태, 작성자 역할 구분, commit SHA | 승인·변경 요청·코멘트 및 승인 취소 이벤트를 구분 |
| 대화·타임라인 | ID, 유형, 시각, 작성자 구분, 연결 URL | 일반 코멘트와 코드 리뷰 코멘트, 봇과 사람을 분리 |
| CI | head/검증 SHA, check run·status 이름, 시작·종료·결론, 조회 시각 | 이전 실행의 미보존·비공개·권한 부족과 실제 실패를 구분 |
| 커밋·릴리스 | SHA, 태그, 공개 시각, PR 연결, 연결 방법 | 태그 포함 관계와 릴리스 노트의 언급을 구분 |
| 절차 문서 | URL, 커밋 SHA 또는 내용 해시, 확인 시각, 적용 범위 | 현재 규정과 과거 실제 운영을 구분 |

인물 식별자는 작성자 본인·다른 사람·봇과 같은 역할 판정에 필요한 범위만 보존한다. 외부 공개 결과는 집계와 사건별 출처 링크 중심으로 작성하고, 개인 순위나 개인별 처리 시간을 만들지 않는다.

각 필드나 사건의 관찰 상태는 아래처럼 기록한다. 빈 문자열, `null`, 0을 하나의 의미로 섞지 않는다.

| 상태 | 의미 | 처리 |
| --- | --- | --- |
| `observed` | 값 또는 사건이 직접 확인됨 | 확인 시점·경로·증거 ID를 연결 |
| `not_observed` | 필요한 공개 경로를 완전히 조회했지만 해당 기간의 사건은 확인되지 않음 | 공개 기록에서의 부재만 의미하며 내부 과정 부재로 확장하지 않음 |
| `unavailable` | 비공개·권한·삭제·보존기간·요청 실패 등으로 조회 불가 | 원인과 재시도 가능 여부 기록 |
| `not_applicable` | 해당 필드가 분석 대상에 적용되지 않음 | 제외 이유와 분모 반영 규칙 기록 |
| `unknown` | 복원 또는 분류에 필요한 근거 부족 | 추정으로 값을 채우지 않음 |

## 3. 수집과 완전성 확인

1. 저장소 ID와 정식 URL을 확정한다. 이동 전후 URL을 중복 저장소로 세지 않는다.
2. REST 또는 GraphQL로 생성 기간의 PR 목록을 수집한다. 검색 API를 쓰면 기간을 작은 구간으로 나누고 페이지를 끝까지 읽는다.
3. GitHub 검색은 검색당 최대 1,000개 결과를 제공하므로 구간별 건수를 확인하고 필요하면 재분할한다. `incomplete_results`와 실제 수집 건수도 확인한다. [공식 검색 API 문서](https://docs.github.com/en/rest/search/search)
4. 리뷰·리뷰 코멘트·일반 코멘트·타임라인 등 중첩 목록도 각각 페이지네이션한다. 첫 페이지만 받아 완료 처리하지 않는다. [공식 페이지네이션 문서](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)
5. 기본 목록을 확보한 뒤 표본 PR의 상세 자료를 가져온다. CI는 check runs와 commit statuses 등 해당 프로젝트가 노출한 경로를 확인한다. [Check runs API](https://docs.github.com/en/rest/checks/runs)
6. 속도 제한·권한·일시 오류를 구분하고, 재시도·대기·재개 위치를 기록한다. 수집량은 첫 주 점검 결과로 추정한다. [공식 속도 제한 문서](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
7. 저장소별 10건을 웹 화면과 대조한다. PR 상태·리뷰·주요 시각·연결을 확인하고 불일치 원인을 기록한다.

인증이 필요하면 공개 데이터 읽기에 필요한 최소 범위의 인증만 사용한다. 토큰은 환경변수로 주입하고 파일·로그에 남기지 않는다. 기본 목록이 불완전하면 전체 건수 기반 지표는 잠정 또는 산출 불가로 표시한다.

manifest에는 `run_id`, 프로토콜 버전, 코드 버전, 저장소 ID, 생성 기간, `snapshot_utc`, 수집 시작·종료 시각, 요청 설정·페이지 수, 수집·실패 건수, 원본 파일 해시, 실행 명령, 누락과 재시도 기록을 남긴다. 원본을 다시 불러오는 것은 나중의 새 수집이고, 기존 원본을 재분석하는 것과 구분한다.

완전성 감사는 목록과 상세 자료를 분리한다. 목록에서는 구간별 API 건수와 고유 PR 수, 중복, 누락 구간을 대조한다. 상세 자료에서는 PR별 리뷰·타임라인·체크의 페이지 완주 여부와 실패 경로를 기록한다. 저장소를 교체하거나 일부 자료를 제외했으면 수집 난도·관찰 가능성 때문인지도 남긴다. 과정이 잘 공개된 저장소만 남기는 선택이 결과에 미친 영향을 한계에 포함한다.

제한된 일부 응답만으로 전체 건수를 확정하지 않는다. 기본 목록이 불완전해도 확인 가능한 사례 설명은 가능하지만, 전체 PR의 비율·빈도라는 표현은 보류한다. 누락 수조차 알 수 없으면 누락률 대신 `산정 불가`와 확인된 범위를 표시한다.

## 4. 표본과 사례 선정

### 기본 목록과 상세 표본

기본 목록은 생성 기간의 모든 PR을 목표로 한다. 봇·자동 생성·사람·불명확을 분류한 후, 사람 작성 PR에서 저장소별 최대 50개를 추출한다. 상태는 추출 조건으로 쓰지 않는다.

고정 규칙은 각 PR에 대해 `SHA256("btw-v1:2026Q3:" + repository_id + ":" + pr_number)`를 계산하고, 해시 오름차순으로 앞 50개를 고르는 것이다. 문자열 인코딩은 UTF-8, ID와 번호는 10진 문자열로 고정한다. 해시 충돌 시 PR 번호 오름차순으로 정렬한다. 실제 구현 시 고정 원본을 이용한 재현 확인을 수행한다.

사람 작성 PR이 50개 미만이면 전수 포함하고 부족분을 기록한다. 자동 생성 여부는 계정 유형, 프로젝트가 문서화한 자동화 계정, PR의 명시적 생성 표시로 판정하며, 이름만으로 불확실한 것은 `unknown`으로 남긴다. 분류 규칙과 수동 수정 내역을 버전 관리한다.

관찰 종료 시 열린 PR·병합 PR·병합 없이 닫힌 PR을 함께 보존한다. 표본에서 특정 상태가 드물어도 결과에 맞춰 표본을 다시 뽑지 않는다.

### 표본 감사와 추론 범위

기본 목록과 상세 표본의 월별 생성 분포, 관찰 종료 시 상태, 확인 가능한 변경 규모를 나란히 보고한다. 변경 규모가 수집 당시 최종값이면 그 한계를 함께 표시한다. 자동화·사람·불명확 비중은 전체 목록에서 별도 보고하고, 상세 표본이 사람 작성 PR만을 대상으로 한다는 점을 명시한다.

고정 해시로 뽑았다는 사실만으로 대표성을 보장하지 않는다. 목록의 누락, 작성자 유형 오분류, 특정 변경 유형의 희소성이 남을 수 있다. 큰 차이를 발견해도 본 표본을 유리하게 교체하지 않고, 다음 버전의 층화 추출 필요성이나 표본 확장을 결정 기록에 남긴다. 보완 사례와 보완 표본은 원래 표본의 빈도 계산에 섞지 않는다.

50개는 탐색 예산이며 효과 검정에 필요한 표본 수를 정당화하지 않는다. 비율을 추정할 때는 표본·모집단 범위와 불확실성 계산법을 명시한다. 통계적 비교를 추가하려면 질문, 필요한 효과 크기, 표본 설계, 가정과 분석법을 먼저 등록하고 이 프로토콜을 개정한다.

### 심층 사례

저장소별 PR 사례 6개는 기능·버그 수정·유지보수·설계 논쟁·미병합·회귀 대응을 가능한 범위에서 포함한다. 이 여섯 유형은 탐색 관점이며 서로 배타적인 통계 분류가 아니다. 별도로 설계 또는 릴리스 자료 2개를 확인한다.

선정 이유, 상세 표본 포함 여부, 부족한 유형을 남긴다. 표본 밖에서 보완한 사례는 보완 사례라고 표시하고 통계에서 제외한다. 흥미로운 사례만으로 해당 관행의 보편성을 주장하지 않는다.

### 분류 코드북과 검토

봇 여부, 변경 유형, 코드 변경 여부, 관련 테스트 여부, 설계 연결, 리뷰 역할, 관행 추출에는 버전이 있는 코드북을 사용한다. 각 항목에 정의, 포함·제외 조건, 복수 분류 허용 여부, 경계 사례, `unknown` 규칙과 예시를 적는다. 코드북과 분류 결과에 버전을 붙이고, 변경 이유와 영향받은 행을 남긴다.

본 분류 전에 첫 주 적합성 점검 자료 중 여러 분야를 포함한 PR 20개를 파일럿 분류한다. 분류가 엇갈리는 항목을 수정하고 코드북을 고정한 뒤 본 표본에 적용한다. 파일럿 자료는 별도 표시하며, 본 표본에도 포함되면 확정 코드북으로 다시 분류한다. 의미를 바꾸는 코드북 수정은 관련된 본 표본 전체에 재적용한다.

저장소별 실제 상세 표본 수의 20%를 올림한 수만큼 고정 규칙으로 골라 분류를 재검토한다(표본 50개일 때 10개). 사람이 두 명 이상 참여하면 서로의 결론을 보지 않고 먼저 분류하고, 항목별 일치·불일치 건수, 원인, 조정 결과를 공개한다. 필요할 때만 척도에 맞는 일치도 통계를 사용하며, 하나의 합격 수치로 판단을 대체하지 않는다. 단독 작업이면 시간을 두고 재분류하고 단독 검토임을 명시한다. 같은 AI의 재실행이나 다른 AI의 동의는 독립적인 사람 검토로 표시하지 않는다. 이 수량은 초기 운영 목표이며 보편적인 연구 품질 기준이 아니다.

| 상태 분포 | 종료 시점 병합·미병합 종료·열림·불명확 수 | 기본 목록. 작성자 유형별로 나눔 |
| 첫 사람 반응 시간 | 생성 후 첫 비작성자 사람의 코멘트/리뷰까지의 시간 | 상세 표본. 봇·작성자 반응 제외, 무반응 수 별도 표시 |
| 첫 공식 리뷰 시간 | 생성 후 첫 비작성자 사람의 제출된 리뷰까지의 시간 | 일반 대화와 분리, draft 포함 시간을 기본으로 표시 |
| 준비 이후 첫 반응 시간 | 최초 ready 시점 이후 첫 비작성자 사람의 반응까지의 시간 | ready 이력 확인 가능 PR만 보조 지표로 산출. 그전에만 반응이 있던 PR은 별도 표시 |
| 병합 소요 시간 | 생성→병합 시간의 중앙값·분포 | 관찰 종료까지 병합된 사람 PR만. 병합 표본 수와 열린 PR의 경과 시간을 병기 |
| 변경 규모 | 변경 파일 수, 추가·삭제 줄 수의 중앙값·분포 | 상세 표본의 값과 측정 시점 표시. 생성 파일·vendor 영향 기록 |
| 공개 리뷰 흔적 비율 | 병합 전 사람 리뷰/대화가 확인된 PR 비율 | 병합 PR 상세 표본. 공식 리뷰와 일반 대화 비율을 구분 |
| 테스트 변경 동반 비율 | 코드 변경 PR 중 관련 테스트 변경이 확인된 비율 | 상세 표본의 코드 변경 PR. 파일명 휴리스틱을 수동 점검 |
| 공개 CI 관찰 범위 | 성공·실패·대기·취소·누락·불명확 분포 | 조회한 SHA와 시점을 명시. 병합 당시 검증이 복원된 사례만 그 시점 지표에 사용 |
| 릴리스 연결 범위 | 포함 태그가 검증된 PR, 노트 언급만 확인된 PR, 미확인 수 | 연결 방법별로 분리. 제품 배포 시각으로 해석하지 않음 |

시간은 달력 시간 기준 UTC로 계산한다. 국가·근무 시간대 추정은 하지 않는다. 각 결과에 `대상 수 / 해당 분모 / 누락 수`를 표시한다. 무반응·미병합 PR을 0시간으로 넣거나 제거해 전체가 빠른 것처럼 계산하지 않는다.

50개 상세 표본은 탐색용이다. 꼬리 분위수와 세부 집단 순위는 피하고, 작은 집단은 건수와 사례 중심으로 제시한다. 전체 분포를 보여줄 때도 언어·변경 규모·봇 비중·공개 범위의 차이를 함께 설명한다.

첫 단계에서는 리뷰 왕복 횟수, 결함 유발률, 배포 빈도, 장애 복구 시간, 개인 생산성은 산출하지 않는다. 공개 PR의 왕복과 실제 작업 단위를 연결하거나 운영 장애와 배포 시점을 확인할 근거가 먼저 필요하다.

### 미완료 사건과 결측 처리

관찰 종료까지 첫 반응이나 병합이 없는 PR은 해당 사건까지의 시간을 끝까지 관찰하지 못한 자료다. 관찰 가능한 경과 시간과 사건 발생 여부를 따로 보존한다. 병합된 PR만의 중앙값은 `관찰 종료까지 병합된 PR에 한정한 값`으로 표시하고, 전체 PR의 예상 처리 시간으로 해석하지 않는다. 병합 없이 닫힌 PR도 병합 대기 시간으로 단순 취급하지 않는다.

최초 분석은 사건 발생 여부와 경과 시간의 기술 통계를 제공한다. 생존분석을 추가한다면 우측 검열, 병합 없이 종료되는 경쟁 사건, 사건 관찰 누락과 가정을 별도 설계해야 한다. 통계 기법을 적용했다는 이유로 공개되지 않은 사건을 복원했다고 주장하지 않는다.

관찰 불가와 불명확은 지표별로 건수·원인을 공개한다. 비율의 분모에 포함될 후보가 총 `N`, 확인된 양성이 `k`, 결과를 확인 못 한 후보가 `u`이면 가능한 범위를 `k/N`부터 `(k+u)/N`까지 보조 표시할 수 있다. 이는 모집단 목록과 적용 대상 `N`이 확정된 경우의 결측 민감도 범위이며 신뢰구간이 아니다. `not_applicable`은 해당 지표의 분모에서 제외하고 제외 건수를 보존한다. 이 범위에서 결론이 달라지면 비교나 추천의 근거를 약화하거나 보류한다.

## 6. 사실·해석·적용 제안

모든 핵심 주장에는 ID를 붙이고 다음 항목을 연결한다.

| 항목 | 내용 |
| --- | --- |
| observation | 직접 관찰한 사실. URL, 사건 시각, 수집 시각, 문서 버전 |
| interpretation | 관찰을 설명하는 해석과 다른 가능한 설명 |
| scope | 적용되는 저장소·기간·변경 유형·표본 수 |
| counterevidence | 맞지 않는 사례, 누락, 공개되지 않은 과정 |
| confidence | 높음·중간·낮음과 그 근거·검토 범위. 보정된 확률이나 효과의 크기를 뜻하지 않음 |
| application | 다른 팀에 제안할 실험과 전제 조건 |

추가로 `claim_type`은 공통 계약의 `policy`(규정), `observation`(사건 관찰), `interpretation`(해석), `effect_hypothesis`(효과 가설), `trial_finding`(대상 팀 시험 결과)을 사용한다. 같은 문장에 섞지 않고 서로 다른 주장 ID로 연결한다. 예를 들어 “소유자 승인을 권장한다”, “표본에서 소유자 승인이 반복 관찰됐다”, “이 방식이 대기를 줄일 수 있다”, “대상 팀 시험에서 대기가 줄었다”는 별개 주장이다.

반복된 관행이라는 주장은 최소 3개 독립 변경 사례를 출발 기준으로 삼고 반례를 찾는다. 3개는 통계적 유의성이나 높은 신뢰도를 보장하지 않는다. 정책 문서의 규정과 실제 준수는 서로 다른 주장으로 남긴다. 문서 한 건으로 확인한 사실은 문서 사실로 기술할 수 있다.

회사 간 우열, 빠른 병합이 높은 품질을 만든다는 인과관계, 코멘트 수가 많은 리뷰가 좋은 리뷰라는 평가는 하지 않는다. 한 카테고리당 한 저장소인 1차 연구에서는 회사 효과와 분야 효과를 분리할 수 없음을 보고서에 명시한다.

### 근거·효과·적합성·검토 상태

다음 상태는 서로 다른 질문에 답하므로 독립적으로 기록한다. `evidence_level`의 수치가 높다고 다른 상태를 자동 승격하지 않는다. 공통 계약의 필드 정의를 사용한다.

| 축 | 값 | 의미 |
| --- | --- | --- |
| `evidence_level` | `E0` provenance-only | 출처가 연결되어 있으나 정책 내용·반복 관찰을 확인한 단계는 아님 |
|  | `E1` source-policy | 출처의 공식 절차·규정을 확인함. 실제 준수나 효과를 뜻하지 않음 |
|  | `E2` repeated-observation | 범위를 명시한 독립 변경 사례에서 관행이 반복 확인됨. 효과 입증은 아님 |
|  | `E3` target-pilot | 대상 팀 시험의 결과 기록이 있음. 긍정·무효·부정 결과 모두 가능 |
| `effect_status` | `untested`, `feasibility_tested`, `target_trial_supported`, `inconclusive`, `contradicted` | 효과 미검증, 실행 가능성만 시험, 대상 시험에서 지지, 판단 불가, 반증을 구분 |
| `advisory_review_status` | `draft`, `ai_checked`, `human_reviewed`, `target_trial_reviewed` | 검토한 주체·범위를 나타냄. 전문가 자격이나 독립성을 자동 보장하지 않음 |
| `transfer_status` | `unassessed`, `conditional`, `eligible`, `blocked`, `trial_supported` | 특정 대상 프로필·제약·추천 버전에 대한 적용 가능성. 전체 팀에 통용되지 않음 |

E2는 앞서 정의한 최소 3개 독립 변경 사례와 반례 검토를 출발 기준으로 삼는다. 같은 변경의 PR·코멘트·커밋을 세 독립 사례로 세지 않는다. E3에는 시험 ID, 대상 조건, 기준선, 기간, 결과와 부작용을 연결한다. 효과가 판단 불가이거나 반증된 E3도 그대로 보존한다.

`target_trial_supported`는 사전 정의한 대상 팀의 기준에 한정한 판정이며 보편적 인과관계를 뜻하지 않는다. 검토 기록에는 검토자, 역할, 검토 시점, 대상 버전, 확인 항목, 미검토 범위와 독립성 여부를 남긴다. AI 자체 평가 점수를 사람 검토나 검증된 확률로 표시하지 않는다.

## 7. 재현·검증과 적용 실험

첫 수집기 검증은 10개 PR의 화면 대조, 중첩 페이지 누락 확인, 동일 원본의 중복 제거·표본 재추출·지표 일치 확인에 집중한다. 수집 도구를 구현할 때에는 실제 실패 위험이 있는 페이지네이션, 종료 시점 상태 재구성, 시간 필드 누락을 검증한다.

분류 검토는 4절의 코드북과 검토 규칙을 따른다. 핵심 주장과 자문에 사용한 패턴은 표본 일부 검토와 별도로 출처·주장 일치 여부를 확인한다. 참여자가 없으면 단독 연구의 한계, 검토한 내용, 미검토 내용을 보고서 첫 부분에 표시한다.

플레이북의 효과는 대상 팀에서 별도 검증한다. 실험마다 문제, 변경할 관행 하나, 사전 기준선, 2주 관찰 지표, 담당 역할, 추가 업무량, 중단 조건을 정한다. 팀의 기준선이 없으면 먼저 기준선을 수집한다. 보고서 완료와 실제 팀에서의 효과 검증은 별도 단계다.

2주는 도입 가능성, 추가 업무, 초기 변화 신호를 확인하는 기본 관찰 창이다. 릴리스 주기나 사건 수에 비해 짧으면 사전에 정한 최소 사건 수·기간에 따라 연장하거나 `inconclusive`로 종료한다. 예를 들어 월 1회 릴리스하는 팀의 배포 안정성은 2주 자료만으로 판정하지 않는다.

기준선과 시험 기간에 팀 구성·업무 유형·변경 규모·성수기·도구가 달라졌는지 기록한다. 속도와 함께 재작업·회귀·검토 부담·팀의 체감 비용을 확인한다. 여러 관행을 함께 바꾸었다면 패키지 전체의 관찰 결과로 남기고 개별 관행의 효과로 분리하지 않는다. 무작위·통제 설계가 없는 전후 차이는 다른 원인으로도 설명될 수 있음을 명시한다.

## 8. AI 추출과 결정론적 계산의 역할

수집·시간 계산·표본 추출·중복 제거·분모·지표 집계는 버전이 있는 코드로 수행한다. AI는 계산 방법이나 코드를 제안할 수 있지만, 보고서의 수치는 고정 원본을 처리한 실행 결과에 연결해야 한다. 문장을 읽고 값을 추정해 최종 지표로 채우지 않는다.

AI는 공개 문서와 사건에서 절차·역할·예외·근거 후보를 추출하고, 코드북에 따라 분류 초안을 만들고, 패턴과 반례를 제안한다. 이후 스키마·출처 검증과 사람 검토를 거쳐 사용 범위를 정한다. 관찰이 부족하면 `unknown`, 조건부 제안 또는 추천 보류를 반환할 수 있어야 한다. 자연스러운 설명만으로 누락 근거를 메우지 않는다.

AI 실행마다 다음을 남긴다.

- 입력 근거 ID·해시, 문서 버전, 관찰 범위, 코드북·스키마 버전.
- 모델 식별자, 제공되는 모델 버전, 프롬프트·설정 버전, 실행 시각과 실행 ID.
- 원래 추출 결과, 근거 위치, 오류·보류, 자동 검증 결과, 사람의 수정과 이유.
- 해당 결과를 사용한 주장·패턴·추천안 ID와 검토 상태.

모델 버전이 제공되지 않으면 그 한계를 기록한다. 같은 입력으로도 AI 출력은 달라질 수 있으므로 원출력을 보존하고, 데이터 재현과 생성 결과의 재생산 가능성을 구분한다. 저장소 본문과 PR 대화는 분석할 자료로 취급한다. 자료 안의 지시문으로 도구 실행·수집 범위·평가 규칙을 바꾸지 않는다.

## 9. 자문·추천에 사용하는 품질 게이트

자문용으로 제시할 수 있는 범위는 AI 사용 여부보다 근거와 검토 상태로 결정한다. OSS 자가 사용에서도 같은 상태·한계가 결과에 표시되어야 한다. 상세 합격 목표와 평가 자료는 [평가 계획](../quality/EVALUATION.md)에 정의하며, 다음 조건은 분석 프로토콜의 최소 요건이다.

| 단계 | 확인할 조건 | 미충족 시 처리 |
| --- | --- | --- |
| 정량 결과 공개 | 목록 범위·분모·결측·측정 시점과 실행 근거를 명시하고 동일 원본 재실행 시 결과 일치 | 잠정·산출 불가로 표시하거나 사례 설명으로 제한 |
| 패턴 등록 | 주장 ID와 직접 근거를 연결하고 반례·대안 설명·선행 조건·적용 제외 조건을 기록 | E0 또는 초안으로 유지하고 확인된 범위만 설명 |
| 팀 맞춤 추천 | 팀 프로필의 필수 정보, 변경 목표, 강제 제약, 의존·충돌·비용, 선택·기각 이유 확인 | 필요한 정보 요청, 조건부 제안 또는 보류 |
| 사람 검토된 자문 | 실제 검토자의 기록과 추천 버전, 출처 확인·제약 검토·부작용 검토 범위 존재 | `draft` 또는 `ai_checked`를 유지하고 미검토임을 표시 |
| 효과 판정 | 사전 기준선·측정법·기간·결과·부작용·혼란 요인 기록 | 효과 미검증 또는 판단 불가로 유지 |

자문에서 사용한 핵심 주장마다 출처가 그 내용을 지지하는지 확인한다. 출처가 존재한다는 사실과 주장이 참이라는 판정은 다르다. 팀 적합성이 확보되어도 효과가 자동 검증되지 않으며, 사람 검토를 받았어도 비공개 내부 과정의 사실 확인으로 표시할 수 없다.

최종 자문 패키지는 팀 프로필과 현재 흐름, 근거가 연결된 병목 가설, 대안과 선택 이유, 현재 대비 변경, 담당·비용·도입 순서, 시험·중단·복구 계획을 포함한다. 어떤 회사에서 시작한 관행인지는 근거 탐색 정보로 보존하되 회사 명성을 추천 점수로 사용하지 않는다. 고객 자료와 공개 저장소 근거는 구별하고, 가상 팀 예시는 실제 고객의 개선 사례로 표시하지 않는다.

## 10. 방법론 참고와 개정

표본 설계와 보고 방법은 [ACM SIGSOFT Empirical Standards](https://www2.sigsoft.org/EmpiricalStandards/docs/standards)와 [표본 추출 보충 기준](https://github.com/acmsigsoft/EmpiricalStandards/blob/master/docs/supplements/Sampling.md)을 참고한다. 이 기준을 참고했다는 사실이 학술 심사 통과나 인증을 뜻하지 않는다.

성과 해석에는 [DORA 공식 지표 안내](https://dora.dev/guides/dora-metrics/)와 [SPACE 연구](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/)를 참고한다. DORA의 현재 안내는 5개 배포 성과 지표를 사용하며 서비스별 맥락을 강조한다. 이 프로젝트의 공개 PR 지표를 배포 빈도·운영 장애·생산성의 대체값으로 부르지 않는다. 속도·품질·협업 부담을 함께 고려하되 측정 가능한 범위만 보고한다.

이 문서의 표본 수·파일럿 수·재검토 비율은 초기 예산과 오류 위험을 고려한 운영 목표다. 첫 수집 이후 실측 비용과 오류를 근거로 수정할 수 있으며, 변경 전후 버전·이유·적용 대상과 기존 결과에 미친 영향을 결정 기록에 남긴다. 결과를 본 뒤 유리한 가설·대상·분모만 고르지 않는다.
